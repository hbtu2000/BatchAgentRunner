# ADR-0001：采用 ADR 记录重大架构决策

- 状态：已接受（Accepted）
- 日期：2026-10-22
- 决策者：架构组
- 关联：ARCH P-14 / A-12；`docs/ARCH-架构重构与工程化治理方案.md` §5.8

## 背景

本仓库在 2026-10 完成了 14 个阶段的重构（facade 拆分、策略对象化、去重、可观测性、CI 门禁）。
但决策依据只散落在提交信息、代码注释与个人记忆里：

- 为什么 `BatchEngine` 要收到 400 行以内？为什么不是按「任务阶段」拆文件？
- 为什么「单一事实来源」落在 Infrastructure 而不是 Core？
- 为什么配置契约宁可横向切片 11 个文件，也不做嵌套分组？

这些问题在半年后无法从代码本身读出答案，重构者只能「考古」提交历史，或者凭直觉再改一遍——
这正是技术债复发的土壤。

## 决策

1. 在 `docs/adr/` 建立 ADR 目录，采用**不可变决策记录**：
   每篇 ADR 含状态/日期/决策者/关联 + 背景/决策/后果/替代方案，决策接受后不修改，变更靠新 ADR 取代旧 ADR。
2. ADR 与代码改动同 PR 提交；PR 描述注明 `ADR-NNNN`。
3. 索引 `docs/adr/README.md` 为唯一入口，文件与索引**双向一一对应**。
4. 机器守卫：`AdrHygieneTests` 校验文件名编号连续、必备章节齐全、索引无漏登记/悬挂链接。
5. 「何时写 ADR」的判定条件写在 README，避免要么不写、要么写成流水账。

## 后果

**正面**

- 决策的上下文与代价可检索、可评审、可追溯；推翻旧决策必须显式写新 ADR，杜绝静默回退。
- 新人接手时先读 ADR 索引即可掌握「为什么长这样」，缩短理解成本。
- 与既有守卫测试体系（`LayeringRulesTests` / `*HygieneTests`）风格一致：文档同步也靠机器，而非人肉 review。

**负面 / 代价**

- 每篇 ADR 有写作成本，需在阶段收口时同步产出；本仓库按「关键决策」而非「每次提交」设阈值控制数量。
- ADR 只记录决策，不替代 DESIGN 文档；两份文本仍可能局部不一致，需靠 PR 评审清单对齐。

## 替代方案

| 方案 | 为什么不选 |
| --- | --- |
| 只写提交信息 | 提交信息按变更粒度切分，缺少横向背景与后果；且不可索引、不可检索 |
| 维护一份「架构决策.md」大文档 | 每次变更都在同一文件叠加，无状态机、无法标记「被取代」，历史被覆盖 |
| 用 Wiki / 外部知识库 | 与代码不同版本、不同评审通道，必然漂移；且 clone 后不可见 |
