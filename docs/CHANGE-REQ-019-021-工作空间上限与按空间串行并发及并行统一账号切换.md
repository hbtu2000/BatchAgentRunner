## REQ-019　工作空间数量上限（精炼 REQ-003a）

### 描述

系统现支持管理多个命名工作空间（`REQ-003a`），但未规定数量上限。为控制配置复杂度和资源占用，**命名工作空间的数量上限默认 10 个（可配置，配置项 `max_workspaces`）**。

- 配置页「工作空间」域的增删改操作受此上限约束：已达配置上限（以 `max_workspaces` 为准）时，「新增工作空间」按钮置灰，且即便通过其他方式提交也明确拦截并提示「工作空间数量已达配置上限（当前上限 N 个）」（提示中的 N 取配置值，非硬编码 10）。
- 导入/加载既有配置时，若工作空间数量已超过配置上限（默认 10 个，历史配置或手工编辑 config.json 导致），预检阶段**告警并拦截启动**，提示用户精简至配置上限以内再启动（**不静默截断**）。
- 该上限作为**可配置项**纳入配置（建议**默认值为 10**），用户在配置页或 `config.json` 中可调整；所有数量校验（新增拦截、预检告警）均以该配置值为准，而非硬编码。
- 配置字段（遵循项目 snake_case 约定）：`max_workspaces`（整数，默认 `10`，下限 `1`；引擎不设置绝对硬上限，以配置值为唯一校验准绳；配置页建议对输入范围作合理 UI 限制（如 1–100）以避免不可维护，但允许高级用户通过 `config.json` 设更大值）。

### 验收标准

- **[Given]** 配置 `max_workspaces = 10`，当前已配置 9 个工作空间，**When** 用户新增第 10 个，**Then** 新增成功，界面显示 10 个。
- **[Given]** 配置 `max_workspaces = 10`，当前已配置 10 个工作空间，**When** 用户再次点击「新增工作空间」，**Then** 操作被拦截，界面提示「工作空间数量已达上限（10 个）」，不创建第 11 个。
- **[Given]** 用户将 `max_workspaces` 调整为 8，当前已配置 8 个工作空间，**When** 用户再次点击「新增」，**Then** 以配置值 8 为准拦截并提示「工作空间数量已达上限（8 个）」（验证上限以配置值为准，非固定 10）。
- **[Given]** 一份 config.json 手工配置了 12 个工作空间且 `max_workspaces = 10`，**When** 启动批处理（预检），**Then** 预检不通过并给出明确告警，定位到具体超限的工作空间条目，要求用户精简后再启动。
- **[Given]** 任意时刻工作空间数量为 N（N ≤ 10），**When** 用户删除其中一个，**Then** 数量降为 N−1，后续可继续新增直至回到 10。

### 与既有需求的关系

- 精炼 `REQ-003a`「支持管理多个命名工作空间，可增删改」：在「可增删改」之上追加数量上限（默认 10，可配置 `max_workspaces`）。
- 不影响工作空间的三级覆盖（任务 > 本批 > 全局，见 REQ-003a）与预检校验（目录不存在/无权限/命名空间悬空）。

### 界面/配置影响

- 配置页「工作空间」域：新增/编辑时的上限校验与提示文案。
- 预检（REQ-010）联动：超限配置作为预检告警项。

### 开放问题

1. （已确认）上限数值（默认 10）作为可配置项 `max_workspaces` 落地，默认 10；校验以配置值为准，非硬编码。
2. 超过上限的历史配置采用「预检拦截」（见描述与验收标准），以杜绝歧义；评审请确认该选择。

## REQ-020　受控并发按工作空间串行（精炼 REQ-012）

### 描述

`REQ-012` 支持可配置并发数（默认 1 即串行），并发任务共享「账号×模型」可用性视图。本需求对并发的**派发粒度**追加一条硬性约束——**工作空间是序列化的基本单位**：

- **同一工作空间内的任务严格串行**：任意时刻，同一个工作空间下最多只有 1 个任务处于 `Running`。
- **不同工作空间之间可以并行**：当待处理任务分布在多个工作空间时，可依据 `Concurrency` 设置并行派发，但每条并行通道**绑定一个独立工作空间**，互不串扰。

等价调度规则：

1. 引擎维护「各工作空间当前在飞任务数」；同一工作空间的在飞数恒为 0 或 1。
2. 派发新任务时，优先从「尚无在飞任务的工作空间」中选取 `pending` 任务派发，直至在飞的**工作空间数**达到 `min(Concurrency, 不同工作空间总数)`。
3. 某工作空间的在飞任务结束后，该工作空间槽位释放，方可派发其下一个 `pending` 任务。

### 边界情形与结论

| 场景                                     | 行为                                                                                  |
| -------------------------------------- | ----------------------------------------------------------------------------------- |
| 本批所有任务都属于**同一个**工作空间                   | 即使 `Concurrency > 1`，也只能串行（在飞工作空间数 = 1 ≤ Concurrency），与串行无异                         |
| 本批任务分布在 **K** 个工作空间（K ≤ Concurrency）   | 最多 K 个并行，每个工作空间 1 个在飞                                                               |
| 本批任务分布在 **K** 个工作空间（K > Concurrency）   | 同时最多 Concurrency 个在飞，每个分属不同工作空间；其余工作空间的 pending 任务排队，待槽位释放                          |
| `Concurrency = 1`                      | 退化为全局串行（既有一期行为），本需求无额外影响                                                            |
| 任务在各工作空间分布**极不均衡**（如 W1 百级任务、W2 仅 1 个） | 有效并行度可能低于 `Concurrency`：W2 完成后其槽位无法复用（W1 已被占用），其余槽位空闲直至 W1 任务陆续完成——此为「按工作空间串行」的固有代价 |

### 验收标准

- **[Given]** 全部 5 个任务都在工作空间 W1，`Concurrency = 4`，**When** 启动批处理，**Then** 任意时刻仅 1 个任务 `Running`，其余排队串行执行。
- **[Given]** 任务分布在 W1、W2、W3，`Concurrency = 2`，**When** 启动，**Then** 初始至多 2 个在飞且分属不同工作空间；当其中一个工作空间的任务完成释放槽位后，第三个工作空间的 pending 任务才能开始。
- **[Given]** 任务分布在 W1、W2、W3、W4、W5，`Concurrency = 4`，**When** 启动，**Then** 同时最多 4 个在飞、各属不同工作空间；第 5 个工作空间的任务必须等待前 4 个中至少一个完成。
- **[Given]** 任意并发场景，**When** 观察运行中任务，**Then** 不存在两个同属一个工作空间的 `Running` 任务。

### 与既有需求的关系

- **精炼 `REQ-012`**：在「可配置并发数 + 可用性共享 + 单写者回写 + 终止顺序」之上，追加「按工作空间串行」派发约束。
- `REQ-012` 的「额度与冷却状态共享」「单写者」「终止顺序」「界面口径」等条款**保持不变**，继续适用。
- 与 REQ-021（并行下统一账号切换）协同：并行通道绑定不同工作空间，但共享同一个**账号身份**（见 REQ-021）。

### 界面/配置影响

- 监控页「当前任务」卡片：仍展示全部 Running 任务，但每个卡片需显示其所属工作空间，便于用户校验「同空间未并行」。
- 配置页「并发」设置：可在 ToolTip 中注明「并发按工作空间串行：同一工作空间内始终串行，不同工作空间可并行」。

### 开放问题

1. `Concurrency` 的语义建议保持为「全局并行通道（在飞任务）上限」，但经 REQ-020 精炼后其实际含义变为：**并行度上界 = `min(Concurrency, 分布有 pending 任务的不同工作空间数)`，且每个工作空间至多 1 个在飞**。即 `Concurrency` 成为并行度的**上界而非保证值**（单工作空间时退化为串行，与 REQ-012 既有「全局在飞上限」框架一致）；与「每工作空间并发数」相比，多空间语义更清晰——请评审确认此语义修订不影响 REQ-012 既有验收。
2. 当某工作空间的任务因依赖（二期 DAG，`depends_on`）被阻塞时：被阻塞任务本就未派发、不占工作空间在飞槽位，故「在飞数为 0 即释放槽位」对其自然成立，无需特殊处理（与 REQ-020 调度规则一致）；本条仅作说明，非阻塞。

## REQ-021　并行执行期间账号切换统一延后（精炼 REQ-012 + 第 3 部分凭证切换）

### 描述

凭证切换专题（设计第 3 部分 §6）明确「同一时刻每个 CLI 只有一个身份」，且「运行中切换只发生在任务边界」。但在 `Concurrency > 1` 时，多个 CLI 子进程**同时读取同一个 Live 凭证位置**，且当前在飞任务共享同一账号身份——若在某任务中途即时切换账号，会导致仍在运行的进程用旧身份、新派发的进程用新身份，**同一时刻在运行的不同任务使用了不同账号**，破坏额度归集与用量统计语义。

因此本需求以「当前在飞任务」为约束单位（不使用「波次」概念），并引入**槽位冻结 + 全局派发暂停**机制，将账号切换严格收敛到「当前在飞任务全部结束后」这一边界（设计 §6 互斥「无运行中进程才允许切换」已从机制上阻止并发下的凭证覆盖；本需求在调度决策层明确上述边界与兜底优先行为）：

- **槽位冻结（slot freeze）**：当某个当前在飞任务免费额度耗尽（或需晋级下一账号 / AuthExpired 需换账号）且任务尚未完成时，立即冻结该任务的在飞槽位；该任务**不切换 Live 凭证**，而是在**原启动账号**上走付费兜底（REQ-004b）继续完成本条任务（不计入失败、不污染误切换率）。
  - **冻结任务的兜底范围限制（关键约束，修复 REQ-004b 跨账号兜底冲突）：** 此处付费兜底**仅限于原启动账号自身的兜底池（`accounts[].fallback_models`）**，不得跨账号选取兜底组合——否则将违背「不切换 Live 凭证」约束，造成并行下账号混用。若原启动账号兜底池无可用组合（或已超成本上限），该任务按 REQ-004b 转入 `waiting`/`blocked`，**不进行跨账号兜底**。
- **全局派发暂停（dispatch halt）**：任一槽位冻结后，调度器立即进入全局派发暂停——**不再向任何槽位派发新任务**（即便其他工作空间的当前任务已自然结束、其槽位空闲，也暂停填充），直到统一切换完成。此举保证切换窗口内不会有新任务以旧账号启动，从源头消除并发下「旧/新账号混用」的竞态。
- **统一切换（unified switch）**：当**当前所有在飞任务结束**（在飞数降为 0，即不含已进入 `waiting`/`interrupted` 等非在飞态的任务）后，调度器执行**一次**账号切换（走第 3 部分 §6 凭证切换流程，含保活回写与原子覆盖），将活动账号置为目标账号；随后**解除派发暂停**，新派发的后续任务均以目标账号身份并行执行。

> **目标账号的确定**：冻结触发时，依据降级矩阵（REQ-004）的遍历顺序记录「后续任务切换目标账号」——即当前活动账号在矩阵中的下一可用账号（如 A → B）。由于规则要求「所有在飞任务始终共享同一活动账号」，任一在飞任务冻结时其下一账号均相同，故多任务并行冻结只会产生**唯一确定的目标账号**，不存在目标冲突。

> **切换后仍不可用 / 全部账号不可用**：若切换后的目标账号 B 自身亦不可用（模型均耗尽或处于时段外），后续任务在 B 上仍会触发兜底并依降级矩阵标注下一目标账号（如 C）；当**全部账号均不可用**且兜底不可用/超限时，按 REQ-004b 转入 `waiting`/`blocked`（遵循 REQ-003b 时段规则 / REQ-004c 冷却规则：界面倒计时，到达任一账号额度重置时间或下一免费时段后自动恢复 `waiting`，仍无可用组合则 `blocked`），而非无约束切换；整个过程**切换次数上界 = 启用账号数**（每个账号至多作为一次切换目标），**不无限循环切换**。

> **单并发退化**：`Concurrency = 1` 或本批仅 1 个工作空间（由 REQ-020 退化为串行）时，不存在「多在飞共享身份」情形，冻结→兜底完成→在飞=0→切换 退化为既有的「任务边界切换」（第 3 部分 §6），本需求不额外约束。

### 调度规则（精炼 REQ-012 并发约束 + 第 3 部分 §6）

1. 当前处于在飞状态的**所有**任务共享同一「当前活动账号」；任一在飞任务的中途账号需求（额度耗尽晋级下一账号、AuthExpired 需换账号等）**不触发对当前在飞任务的即时切换**。
2. 当某个在飞任务触发切换需求时：
   - **冻结该在飞槽位**，并立即进入**全局派发暂停**（不再派发任何新任务）；
   - 该任务在**原启动账号**上立即触发付费兜底（REQ-004b）完成本条任务（不切换 Live 凭证），不计入失败、不污染误切换率（兜底仅限原启动账号自身的 `accounts[].fallback_models` 兜底池，不跨账号；见上文「冻结任务的兜底范围限制」）；
   - 引擎依据降级矩阵记录「后续任务切换目标账号」（唯一确定，见上文）；若兜底不可用或已超成本上限，该任务按 REQ-004b 转入 `waiting`/`blocked`，派发暂停与切换标注仍生效。
3. 当**当前所有在飞任务结束**（在飞数降为 0；已进入 `waiting`/`interrupted` 的任务不计入在飞、不阻塞本次切换，与第 2 条一致）后，引擎执行**一次**账号切换（§6 流程）至目标账号；随后**解除派发暂停**，后续任务以目标账号并行派发。
4. 整批全程，任意时刻处于在运行状态的任务始终使用同一账号身份；账号切换只作用于「当前在飞任务全部结束后才派发」的后续任务。

### 验收标准

- **[Given]** `Concurrency > 1` 且多个任务在飞、共用账号 A，**When** 其中某任务因额度耗尽需切换到账号 B，**Then** 该任务槽位立即冻结并进入全局派发暂停，不切换 Live，立即触发付费兜底在账号 A 上完成本条任务，并标注「后续任务切换目标 = B」；**冻结期间不向任何槽位派发新任务**；**当所有当前在飞任务结束后**，引擎统一切换为账号 B 并解除派发暂停，之后新派发的后续任务均以账号 B 并行执行（已完成任务不再重跑）。
- **[Given]** 某任务冻结进入派发暂停后、其余在飞任务分布在不同工作空间仍继续运行，**When** 观察调度器派发行为，**Then** 即便某工作空间当前任务已自然结束、其槽位空闲，调度器也**不向该槽位填充新任务**，直至统一切换完成、暂停解除。
- **[Given]** 任意并行执行时刻，**When** 检查所有当前在运行的 CLI 子进程加载的 Live 凭证文件哈希或日志中的账号标识，**Then** 它们的身份一致（均等于当前活动账号），不存在「部分旧账号、部分新账号」；且冻结/派发暂停期间无新进程以旧账号启动。
- **[Given]** 并行执行中某任务因额度耗尽走兜底完成，**When** 报告中统计账号使用量与切换时间线，**Then** 该任务记为「原账号 A + 兜底模型」完成（不记录账号切换事件）；账号切换事件只在「当前在飞任务全部结束后」记录一次（后续任务统一切换），不记录逐任务切换；误切换率指标不受影响（兜底完成属预期调度行为）；报告须包含 `deferred_switch` 延后切换标记（**该字段由 REQ-021 新增，须同步追加至 REQ-011 汇总报告 schema 与第 11 章埋点表**：作为 `account_switched` 时间线条目的布尔属性 `deferred_switch = true`，用于区分「并发下延后统一切换」与常规任务边界切换；另新增埋点事件 `slot_frozen`、`account_switch_deferred` 记录冻结与延后标记，见「界面/日志影响」与影响面分析）。
- **[Given]** `Concurrency = 1`（串行），**When** 任务额度耗尽需切换，**Then** 在任务边界按既有逻辑切换，行为与 REQ-021 介入前一致（冻结→兜底→在飞=0→切换退化为任务边界切换）。

### 与既有需求的关系

- **精炼 `REQ-012` 并发约束**：并发下，当前在运行任务的账号切换从「即时各自切换」改为「冻结在飞槽位 + 全局暂停派发 + 兜底完成当前任务 + 延后到当前在运行任务全部结束后对后续任务统一切换」。
- **精炼第 3 部分凭证切换 §6「运行中切换只发生在任务边界」**：在并发场景下明确「当前在运行任务中途不切换」；通过「槽位冻结 + 全局派发暂停」保证切换窗口内无新任务以旧账号启动，切换只在「当前在运行任务全部结束」这一边界执行一次，与 §6 互斥「无运行中进程才允许切换」一致。
- 不影响：凭证快照/保活回写/Vault 机制、额度冷却登记（REQ-004c）、降级矩阵遍历（REQ-004，仅用于确定唯一目标账号）、兜底（REQ-004b）。

### 界面/日志影响

- 运行日志：并行执行中检测到「需切换账号」时，记录 `slot_frozen`（文案「并行执行中，在飞槽位已冻结、进入全局派发暂停；当前在飞任务走付费兜底在原账号完成」）与 `account_switch_deferred`（文案「账号切换已延后至当前在飞任务全部结束后执行」）；实际切换（在「当前在飞任务全部结束后」触发一次）仍记 `account_switched`。
- 监控页状态：派发暂停期间应在「当前任务」区或批级状态栏明确展示「派发已暂停（等待在飞任务结束并统一切换账号）」状态，便于用户理解为何无新任务启动。
- 监控页 toast：并行执行中检测到需切换账号时，提示「并行执行中，当前在飞任务将用付费兜底在原账号完成，账号将在当前在飞任务全部结束后统一切换；期间暂停派发新任务」而非即时切换提示。


### 已确认的设计决策

1. （已明确）进入 `waiting`/`interrupted` 的任务不再占在飞槽位、不阻塞统一切换；当其余在飞任务结束、在飞数降为 0 时触发统一切换（waiting/interrupted 任务不计入在飞、不阻断本次切换）——本文已按此处理。
2. （已明确）多任务并行冻结的目标账号冲突问题：因规则要求「所有在飞任务始终共享同一活动账号」，任一在飞任务冻结时其降级矩阵下一账号唯一确定，不存在目标冲突；本文按「冻结时记录降级矩阵下一账号为统一目标账号」处理。
3. （已明确）用户中途手动「切换到此账号」（第 3 部分 §7 界面能力）在仍有当前在运行任务（含派发暂停期间）时**禁用**；仅允许在当前在飞任务全部结束后（in-flight = 0，含派发暂停自然结束）或串行态操作；in-flight = 0 时的手动切换立即执行（同 §6）并清除 pending 切换目标。

### 风险与待评审关注

1. **派发暂停期间的吞吐坍塌（关键副作用）：** 触发槽位冻结后进入全局派发暂停，即便其他工作空间的在飞任务自然结束、其槽位空闲，也不再派发新任务，直至冻结任务（在兜底下）完成、在飞数归 0。因此**在冻结窗口内，并行度实际坍塌为该冻结任务（及其余仍在跑的在飞任务）单独执行**，不再有新任务启动。若冻结任务为长耗时任务，会造成明显的并行度损失。此为「杜绝并发账号混用」的固有代价，已被验收标准第 2 条明确；落地时建议在监控页清晰展示「派发已暂停（等待在飞任务结束并统一切换账号）」状态（见「界面/日志影响」），并评估是否需要补充「暂停期间仍可在原账号 A 上继续派发同账号新任务」的折中（注：该折中会推迟统一切换时机，需另行评审，本文暂不采用）。
2. **新增报告/埋点字段：** `deferred_switch`（REQ-011 报告字段，挂在 `account_switched` 时间线条目上）、`slot_frozen` 与 `account_switch_deferred`（第 11 章埋点事件）为 REQ-021 新增，须同步追加至 REQ-011 汇总报告 schema 与第 11 章埋点表（见验收标准 4 与影响面）。
3. **REQ-004b 兜底语义需同步收窄：** REQ-021 对并发冻结任务的兜底施加「仅限原启动账号兜底池、不跨账号」约束，与 REQ-004b 全局「账号顺序 × 账号内兜底池顺序」兜底选取存在范围差异，须在 REQ-004b 章节同步注明此并发特例，避免落地时误解（见影响面分析「兜底」行）。
