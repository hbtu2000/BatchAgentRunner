## 1. 执行摘要

**简述：** 构建一个本地批处理任务调度工具：将一批任务保存在任务文件中，工具循环读取任务并调用 WorkBuddy / CodeBuddy（Agent CLI）逐个处理，处理结果写回文件，全程有实时进度界面，可随时终止。

**内容：** 任务文件驱动的「AI Agent 批处理器」+ 双维度额度自动降级（**账号池轮换 + 每账号独立的候选模型池** fallback，模型配置挂在账号下：同一模型可在不同账号下配置不同的免费时段与优先级，默认降级策略为**模型优先**：同账号先轮换其自有候选模型，该账号模型全耗尽再换账号）+ **免费模型时段可用性配置**（时段按「账号下的模型项」配置，未设则全天可用）+ **额度重置时间感知**（额度耗尽即记录组合重置时间点，冷却期内跳过该组合，全部冷却时按最早恢复时间等待或阻塞）+ **每账号独立的兜底模型池** + **专家/专家团配置** + 实时监控界面。

**原因：** 当前逐条向 AI 助手提交任务、复制粘贴结果的过程高度重复且无法规模化；免费额度用完后任务中断，需要人工换账号或换模型重试。本工具将「提交—等待—回写」全流程自动化，额度耗尽时自动在「账号池 × 模型候选」矩阵中切换到下一个可用组合并继续执行；同时支持指定 WorkBuddy 专家或专家团来执行任务，实现无人值守的批处理。

**面向谁：** 需要批量处理任务（如批量改代码、批量生成文档、批量分析文件）的开发者与重度 AI 工具用户。

**成功标准：**

- 一次性配置后，≥ 50 条任务可无人值守跑完，结果完整回写
- 模型额度耗尽时**应触发必触发**地自动切换到下一个可用组合（漏判率 0，误切换率 ≤ 5%），任务不丢失、不断档
- 界面实时反映每条任务状态，用户可随时安全终止且已完成的进度不丢失

**时间表：** 一期（MVP）先行，二期演进为「软件工程流程自动化」（见第 15 章）。

## 2. 问题陈述

### 当前情况

当前，用户在需要批量处理任务时（例如：对一批文件逐一执行 AI 处理、对一批代码模块逐一做修改），必须在 AI 工具中逐条手动提交，等待结果后手动复制回文件。此外，各模型/工具存在免费额度限制，额度用完后任务中断，用户需要人工换模型、找到断点、重新继续。

### 影响

**受影响的人：**

- 批量任务发起者：重复劳动、耗时、易漏
- 使用免费额度的用户：任务频繁中断，断点难恢复

**问题规模：**

- 每个批量任务需 N 次手动「提交—等待—回写」循环（N = 任务条数）
- 额度耗尽后若无人干预，剩余任务全部停滞

### 证据

- 用户（本人）明确提出的诉求：批处理 + 自动换模型 + 实时界面 + 可随时终止
- 该场景是典型的「人肉编排 Agent」痛点，业界同类需求（agent 编排器、task runner）持续增长

### 替代方案评估与自建理由

| 方案               | 描述                               | 为何不采用                                                                 |
| ---------------- | -------------------------------- | --------------------------------------------------------------------- |
| A. 纯脚本循环         | 用 shell/Python 循环调 CLI，自行管理状态与回写 | 需自建断点续跑、原子回写、实时界面、安全约束，最终仍要做一个「工具」，且双维度降级逻辑重复造轮子                      |
| B. 通用 Agent 编排框架 | 采用开源 task runner / 编排器           | 不绑定 WorkBuddy/CodeBuddy CLI 的「账号池 × 模型」额度矩阵与专家体系，双维度降级需自行扩展，改造成本不低于自建 |
| C. 直连各模型 API     | 绕过 CLI，直接调模型 API                 | 放弃 CLI 的无人值守模式与专家/专家团能力，与「沿用熟练 CLI 工作流」的前提冲突                          |

**结论：** 自建。差异化聚焦在三点：CLI 适配层（统一 WorkBuddy/CodeBuddy 差异）、双维度额度自动降级、以任务文件为状态源的断点续跑。

## 4. 目标与成功指标

### 业务目标

1. **实现无人值守批处理**
   - 当前状态：每条任务需人工提交与回写
   - 目标：一次配置，全自动跑完一批任务
   - 影响：释放人力，任务规模不再受人力限制
2. **消除额度中断**
   - 当前状态：额度耗尽即中断，需人工换模型
   - 目标：自动降级到下一个可用组合（默认同账号先换模型），断点任务以完整指令继续执行；额度耗尽的组合记录重置时间，冷却期内不再重试，全部组合冷却时按最早恢复时间点自动等待
   - 影响：任务完成率接近 100%

### 用户目标

1. 把一批任务写进文件（或界面导入），点一下就自动全部处理完
2. 实时看到每条任务的状态与处理结果
3. 随时终止，且已完成部分不丢失、可续跑

### 成功指标

| 指标                 | 基线       | 目标                                  | 时间表   | 优先级 |
| ------------------ | -------- | ----------------------------------- | ----- | --- |
| 批处理任务自动完成率         | 0%（纯手工）  | ≥ 95%，且失败任务 100% 具备明确错误归因与日志（无静默失败） | 一期发布时 | P0  |
| 降级机制触发率（漏判率）       | 0%（人工切换） | 应触发必触发 100%（漏判率 0）                  | 一期发布时 | P0  |
| 误切换率（临时限流被误判为额度耗尽） | —        | ≤ 5%（阈值经 M0 V-3 校准后写入配置）            | 一期发布时 | P0  |
| 终止后已完成任务保留率        | 无此能力     | 100%（终止不丢已完成结果）                     | 一期发布时 | P0  |
| 界面状态刷新延迟           | 无界面      | ≤ 2 秒                               | 一期发布时 | P0  |
| 额度冷却有效性            | —        | 冷却期内的无效调用次数 = 0（重置时间前不对已耗尽组合发起调用）   | 一期发布时 | P0  |

**反向指标**（监控负面影响）：

- 重复执行率：同一任务不应被重复处理（幂等性）；不应 > 1%
- 结果文件损坏次数：应为 0（回写需原子写入 + 启动前自动备份）
- 兜底费用超限触发次数：应为 0（超限必须停用兜底并转 blocked）

## 5. 用户画像与用例

### 主要画像：批量任务处理者

- 角色：开发者 / 技术效率用户
- 经验水平：中级及以上，熟悉 WorkBuddy / CodeBuddy CLI
- 目标：把重复性 AI 任务一次性交给工具跑完
- 痛点：手动逐条提交慢；额度中断烦；无法监控进展

### 用例

#### 用例 1：批量处理任务文件（主流程）

**场景：** 用户准备了一个任务文件（如 `tasks.json` / `tasks.md`），内含 30 条待处理任务。  
**用户目标：** 启动工具后，30 条任务被逐条（或受控并发）调 WorkBuddy/CodeBuddy 处理，结果逐条写回任务文件（Markdown 格式写入 sidecar 结果文件，见 REQ-001/006），全程无需人工干预。  
**当前行为：** 手动逐条提交、复制结果。  
**期望行为：** 启动即跑完；界面实时显示「处理中 / 完成 / 失败 / 已中断」；续跑时自动跳过已完成任务并显示「已跳过 N 条」计数。  
**频率：** 每周多次。

#### 用例 2：额度耗尽自动换模型 / 换账号

**场景：** 任务执行到第 12 条时，当前「账号 1 + 模型 A」组合的免费额度耗尽（API 返回配额/限费类错误）。  
**用户目标：** 工具自动切换到下一个可用组合（优先同账号换模型，该账号模型也耗尽再换账号），**当前任务以完整指令重新执行**（而非从头重跑整批、也不是放弃断点），批处理整体从断点继续。  
**当前行为：** 报错中断，用户人工换账号/换模型、找回断点。  
**期望行为：** 自动切换 + 当条任务自动重试；界面提示「模型 A 额度已用尽，已切换至模型 B（账号 1）」；额度耗尽的组合记录重置时间点，重置前直接跳过（界面提示预计恢复时间），全部组合冷却中时按最早恢复时间等待或阻塞；若某候选模型设置了免费时段且当前处于时段外，该模型直接跳过（不视为额度耗尽、不触发告警），有即将进入时段的模型时可等待至时段开始。  
**频率：** 常态化发生。

#### 用例 3：指定专家/专家团执行

**场景：** 某批任务是「给 20 个模块补充单元测试」，用户希望由擅长编码的专家（或一个「测试专家团」）来执行，而非默认智能体。  
**用户目标：** 在配置中选择一个专家或专家团，批处理中每条任务都由其执行。  
**期望行为：** 调用 Agent 时携带专家/专家团参数，界面显示当前执行的专家身份；未选择时使用默认智能体。  
**频率：** 按任务类型按需配置。

#### 用例 4：随时终止与续跑

**场景：** 用户临时需要机器资源，或发现任务描述有误，希望立即停止。  
**当前行为：** 强杀进程可能丢失状态。  
**期望行为：** 点「终止」后当前任务**安全中断**（默认立即中断；可选「等待当前任务完成后再终止」），状态与结果落盘；之后可「续跑」只处理未完成任务。  
**频率：** 按需。

#### 用例 5（边缘）：任务本身执行失败

**场景：** 某条任务因描述错误或依赖缺失，所有候选模型都失败。  
**期望行为：** 标记为「失败」，记录错误详情，不阻塞后续任务；批处理结束后汇总报告失败清单。

## 6. 用户故事与验收标准

### Epic 1：任务文件与批处理引擎

#### 故事 1.1：任务文件加载与解析

**作为** 批量任务处理者  
**我想要** 工具能读取我定义好的任务文件（支持 JSON / Markdown 两种格式）  
**以便** 我可以用自己习惯的方式准备任务清单

**验收标准：**

- [ ] **给定** 一个合法的任务文件（JSON 数组或 Markdown 任务清单），**当** 工具加载它，**那么** 每条任务被解析为独立任务项，包含：任务 ID、任务描述/指令、状态（pending）、结果（空）
- [ ] **给定** 一个格式非法的任务文件，**当** 工具加载它，**那么** 给出明确的错误定位（第几条/哪一行），不启动执行
- [ ] **给定** 任务文件，**当** 部分任务已带有结果（上次运行遗留），**那么** 默认跳过已完成任务（支持「强制重跑」开关，见 REQ-008）
- [ ] **给定** 某条任务的指令跨多行书写，**当** 工具加载它，**那么** 自 `- instruction:` 行起至下一个二级标题（或文件结尾）的全部内容合并为该任务的完整指令（见 REQ-001 与附录 A）（v1.10 新增，对应评审 R-9）
- [ ] **给定** 任务缺失 ID / ID 重复 / 引用的命名工作空间悬空，**当** 工具加载它，**那么** 按 REQ-001a / REQ-003a 规则处理（自动生成回写 / 报错定位）

**优先级：** P0

#### 故事 1.2：循环调度执行

**作为** 批量任务处理者  
**我想要** 工具按顺序循环读取任务并逐条调用 WorkBuddy 或 CodeBuddy 处理  
**以便** 我不需要人工参与执行过程

**验收标准：**

- [ ] **给定** N 条 pending 任务，**当** 批处理启动，**那么** 工具按顺序逐条调用指定的 Agent CLI，每条任务执行完毕后将结果写回任务文件，再执行下一条
- [ ] **给定** 执行配置了「执行工具」（WorkBuddy / CodeBuddy），**当** 启动，**那么** 使用对应 CLI 以无头/非交互方式执行任务指令
- [ ] **给定** Agent 执行中弹出任何交互式询问（权限确认、方案选择等），**当** 无人工介入，**那么** 系统自动选择默认选项继续执行，任务不因等待输入而挂起（危险操作确认除外，见 REQ-002b）
- [ ] **给定** 某条任务执行抛出异常，**当** 处理该任务，**那么** 按重试策略重试（默认 2 次），且受单任务总尝试/总时长上限约束（REQ-009a），仍失败则标记失败并继续下一条，不阻塞整批

**优先级：** P0

#### 故事 1.3：结果回写

**作为** 批量任务处理者  
**我想要** 每条任务处理完成后结果立即写回任务文件  
**以便** 中断/崩溃时已完成的结果不丢失

**验收标准：**

- [ ] **给定** 一条任务执行成功，**当** 写回结果，**那么** 任务状态更新为 done，结果字段、使用模型、使用账号、执行专家、耗时、时间戳一并写入
- [ ] **给定** 回写操作，**当** 执行写入，**那么** 采用「写临时文件 + 原子替换」方式，避免写入过程中断导致文件损坏
- [ ] **给定** 工具在任意时刻被强杀，**当** 重新打开任务文件，**那么** 文件格式完好，已完成任务的结果完整存在
- [ ] **给定** Markdown 格式任务文件，**当** 结果写回，**那么** 写入同目录 sidecar 结果文件，不改动用户 Markdown 原文（见 REQ-001/006 与附录 A）

**优先级：** P0

### Epic 2：模型候选与额度自动降级

#### 故事 2.1：账号候选模型池配置

**作为** 批量任务处理者  
**我想要** 为账号池中的每个账号分别配置一个有序的候选模型池（如 A 账号 [Hy4, 模型B]、B 账号 [Hy4, 模型C]），不同账号的模型池相互独立  
**以便** 按每个账号实际可用的模型与偏好依次尝试（v1.12 修订：候选模型池挂在账号下，不再全局共享）

**验收标准：**

- [ ] **给定** 配置界面/配置文件，**当** 我为某个账号设置候选模型池，**那么** 每个账号拥有自己独立的有序模型列表，支持增删与拖拽排序，首个为该账号的首选模型
- [ ] **给定** 不同账号配置了不同（或同名但参数不同）的候选模型池，**当** 启动批处理，**那么** 从首选账号的候选池第一个模型开始执行，降级时只在该账号自己的候选池内轮换
- [ ] **给定** 某账号未配置候选模型池，**当** 启动批处理，**那么** 回退到全局共享候选模型列表（向后兼容，见 REQ-003）；两者均未配置时预检告警（v1.12 新增）

**优先级：** P0

#### 故事 2.2：额度耗尽自动切换

**作为** 批量任务处理者  
**我想要** 当某模型免费额度用完时，工具自动切换到下一个候选模型并继续当前任务  
**以便** 我不用半夜爬起来换模型

**验收标准：**

- [ ] **给定** 当前模型返回额度类错误（配额耗尽 / 余额不足 / 限流上限达成长期态），**当** 错误被识别，**那么** 自动将当前任务切换到候选列表中的下一个模型重试（以该任务的完整指令重新执行），批处理从断点继续，不重跑已完成任务
- [ ] **给定** 已切换到列表最后一个模型仍额度耗尽，**当** 无更多候选，**那么** 批处理暂停（批级状态：blocked），界面提示所有模型额度已尽；恢复后（用户补充额度/模型）可续跑（注：因全部模型处于免费时段外导致的不可用，按故事 2.6 的时段规则处理，不计入本条）

#### 故事 2.5：特殊模型兜底（断点任务收尾）

**作为** 批量任务处理者  
**我想要** 当一条任务尚未完成、而免费组合全部不可用（额度耗尽，或全部模型处于免费时段外）时，用预设的特殊模型（付费）把它收尾，然后后续任务继续用免费组合  
**以便** 不把已投入的时间浪费掉，也避免任务被迫进入 blocked 后人工介入

**验收标准：**

- [ ] **给定** 当前任务未完成（Agent 已投入执行、可能已产生部分磁盘产出），**当** 免费组合矩阵当前不可用（额度耗尽，全部组合处于免费时段外，或全部组合处于额度冷却中），**那么** 若兜底已开启且未超成本上限，自动按「账号顺序 × 该账号兜底池顺序」选取第一个可用兜底模型完成当前任务（同样以完整指令重新执行）；完成后任务标记 done，且记录「兜底模型（及所在账号）」与实际花费（或估算花费并标注口径）（v1.12 修订）
- [ ] **给定** 兜底完成了当前任务，**当** 批处理继续，**那么** 下一条任务回到正常降级逻辑（下一个免费账号 + 首选免费模型），不延续使用特殊模型
- [ ] **给定** 兜底未开启或成本上限已用尽，**当** 免费组合当前不可用（额度耗尽、全部模型处于时段外或全部组合冷却中）且任务未完成，**那么** 当前任务标记 interrupted（保留已产出的中间结果并写回任务文件），批处理进入 blocked 或 waiting（按 REQ-003b 时段规则 / REQ-004c 冷却规则），可续跑
- [ ] **给定** 兜底发生，**当** 用户查看界面/报告，**那么** 有明确的「兜底使用」标识（P0 阶段：任务卡片 + 切换事件 + 运行日志；汇总报告中的花费统计随 P1 报告交付，见 Epic 4 / REQ-011）（v1.10 修订，对应评审 R-11）
- [ ] **给定** 用户为各账号配置兜底模型池（每账号独立、有序）并设置成本上限，**当** 保存配置，**那么** 支持按账号分别设置兜底模型池（至少一个账号配置了兜底模型即视为具备兜底能力），兜底总开关与单任务/单批成本上限为全局配置（默认关闭兜底）（v1.12 修订：兜底模型池挂在账号下）
- [ ] **给定** 兜底模型被触发，**当** 遍历兜底组合，**那么** 按账号顺序 × 该账号兜底池顺序选取第一个可用兜底组合；兜底模型不参与免费时段过滤（保证收尾能力，见 REQ-004b）（v1.10 新增对应评审 R-3；v1.12 修订）

**优先级：** P0

#### 故事 2.6：免费模型时段可用性配置

**作为** 批量任务处理者  
**我想要** 为各账号候选池中的模型项配置「免费时段」（未配置则视为全天可用），且同一模型在不同账号下可配置不同时段

### 边缘情况

1. **任务文件在运行中被外部修改**
   - 预期行为：以工具内存中的任务列表为准继续执行；界面提示检测到外部修改；不自动合并
   - 理由：避免外部修改与回写互相覆盖，保证数据一致性
2. **Agent CLI 本身不可用（未安装/未登录）**
   - 预期行为：启动前预检，给出明确指引；不进入执行循环
3. **同一任务连续失败**
   - 预期行为：重试 N 次（默认 2）后标记 failed，跳过并继续；可选「失败即停」开关（默认关，P1，见 REQ-013）；总尝试次数受 REQ-009a 上限约束
4. **超长任务（Agent 执行超过阈值时间）**
   - 预期行为：单任务超时上限可配置（默认 10 分钟，标注为假设，需按实际任务类型校准），超时按失败处理并记录已产生的部分输出；单任务总时长（含全部重试与切换）另受 REQ-009a 总上限约束
5. **Agent 在无官方无人值守参数的场景下仍尝试交互（如 stdin 等待输入）**
   - 预期行为：检测到 stdin 等待（无输出增长超阈值）时自动注入默认应答；无法注入则按超时失败处理，不挂起整批
   - 理由：兜底保证「零人工介入」，配合 REQ-002a 与 REQ-010b 落地
6. **自动应答遭遇危险操作确认（删文件、改系统配置、git push --force 等）**
   - 预期行为：不自动批准；命中危险模式黑名单的，该任务标记 failed（错误信息注明命中黑名单及具体交互点），不阻塞整批；白名单内的操作按默认应答执行并记日志
   - 理由：无人值守不能把单次误操作放大为整批破坏，见 REQ-002b 与第 14 章风险表
7. **已开启自动关机，但批处理被终止 / 进入 blocked / 失败率超阈值**
   - 预期行为：不执行关机，界面与汇总报告标注「已开启自动关机但未满足触发条件」及原因
   - 理由：避免在异常或有遗留问题的状态下关机，导致用户无法及时干预
8. **关机倒计时期间用户不在场且倒计时结束**
   - 预期行为：按配置执行关机；所有结果与报告在此前已 100% 落盘，关机不造成任何数据丢失
   - 理由：落盘优先于关机是硬性顺序约束
9. **任务部分完成后免费组合当前不可用（额度耗尽，或全部模型处于免费时段外），但兜底未开启/超成本上限**
   - 预期行为：任务标记 interrupted 并保留已产出的中间结果（写回任务文件），批处理进入 blocked；续跑时用户可选择「重跑该任务」或「人工处理」
   - 理由：部分成果不丢弃，兜底是可选保险而非强制
10. **特殊模型本身也失败**
    - 预期行为：按普通失败处理（重试 → failed），不产生循环兜底；兜底花费照实记录
    - 理由：兜底是收尾手段，不能变成无底洞
11. **任务指定的工作空间目录不存在 / 被删除 / 无权限 / 命名空间悬空**
    - 预期行为：启动前预检直接拦截并定位到具体任务与空间配置；运行中目录被外部删除则该任务按失败处理（错误信息指明空间问题），不阻塞后续任务；任务引用的命名空间被重命名/删除导致悬空的，加载时报错并定位到具体任务
    - 理由：空间错误若不拦截，任务会在错误目录执行，产出难以追溯
12. **任务执行中跨越免费时段边界（进入或离开某模型的免费时段）**
    - 预期行为：在途任务不中断、不因时段切换而失败；该任务完成后，下一条任务按新的时段视图重新评估可用模型
    - 理由：时段是调度维度而非执行约束，中断在途任务会浪费已投入的执行
13. **CLI 返回的额度重置时间不可靠（早于当前时刻 / 异常超长值 / 与本机时钟偏差大）**
    - 预期行为：解析出的重置时间早于当前时刻或无法解析时视为解析失败，降级为默认冷却时长（标注数据来源）；超长值按正常记录，但超出「最长可等待时长」时直接 blocked 提示，不空等
    - 理由：不可靠的重置时间比没有重置时间更危险（会导致错误等待或错误恢复），宁可退化为保守的默认冷却

### 必须有 (P0) - 发布阻断项

- **[REQ-001]** 系统应支持从文件加载任务清单，一期支持 JSON 与 Markdown 两种任务文件格式
  - JSON 格式：原地原子回写（临时文件 + 替换）
  - Markdown 格式：**只读输入源**，执行状态与结果写入同目录 sidecar 结果文件（`<任务文件名>.result.json`），续跑以 sidecar 为准；Markdown 原地回写列入二期（见第 3 章范围外）
  - Markdown 解析约定：每个二级标题 `## <task-id>` 为一条任务，其下 `- instruction:` 行为任务指令起始；指令可跨多行，至下一个二级标题（或文件结尾）结束，多行内容合并为该任务的完整指令（附录 A）（v1.10 修订，对应评审 R-9）
  - 理由：任务文件化是一期核心场景，格式需覆盖结构化（JSON）与轻量手写（Markdown）两类习惯
- **[REQ-001a]** 系统应定义并执行任务 ID 规则（断点续跑与幂等性的唯一依据）：
  - ID 缺失时按序号自动生成（`task-001` 形式）并回写文件（Markdown 则写入 sidecar）
  - ID 重复、含非法字符时，加载阶段报错并定位到具体任务，不启动执行
  - 启动时记录本批 ID 集合快照；续跑时检测「已 done 的 ID 消失或被修改」，给出明确提示并要求用户确认（防止手改 ID/重排文件导致已完成任务被重跑，对应反向指标「重复执行率 ≤ 1%」）；开启「强制重跑」（REQ-008）时，该确认降级为一次性告知，不强制弹出（v1.10 新增，对应评审 R-10）
  - 理由：ID 规则是续跑幂等的地基
- **[REQ-002]** 系统应按顺序循环读取任务，逐条调用 WorkBuddy 或 CodeBuddy（可配置，一期单选其一）以非交互/无头模式执行，并将结果写回任务文件
  - 理由：批处理主流程
- **[REQ-002a]** 执行全程应零人工介入：Agent 运行中出现的任何交互式询问（工具权限确认、方案/计划选择、继续或重试等）应自动选择默认选项
  - 实现要求：优先使用 CLI 的官方无人值守参数（如自动批准/跳过确认类开关）；对无开关的交互场景，自动应答默认项
  - 例外：危险操作确认不自动批准，见 REQ-002b
  - 理由：无人值守是批处理的根本前提，任何卡在等待输入的任务都会阻塞整批
- **[REQ-002b]** 系统应对自动应答提供危险操作防护：
  - 维护高危操作模式黑名单（文件删除、系统配置修改、git push/force 等，初始清单由 M0 V-9 结论校准）
  - 命中黑名单的确认请求：不自动批准，该任务标记 failed 或 blocked 并记录命中的交互点
  - 支持配置「自动允许范围」白名单，白名单内的确认按默认应答执行
  - 与 REQ-010b 联动：高危确认点在日志中醒目标记
  - 理由：无人值守 + 自动批准可能把单次误操作放大为整批破坏（批量改代码场景尤甚）
- **[REQ-003]** 系统应支持配置多账号池，且**每个账号拥有自己独立的有序候选模型池**（candidate model pool），并从「首选账号 + 该账号首选模型」组合开始执行（v1.12 修订）
  - **候选模型池挂在账号下**：模型池是账号的子配置（`accounts[].model_candidates`），账号池内各账号的模型池相互独立——不同账号可配置不同的模型集合、不同的排序、乃至同名模型的不同免费时段（v1.12 修订，推翻 v1.10 R-1 的「全局共享列表」决策，见第 13 章产品决策记录）
  - 降级矩阵 = 各启用账号与其**自有**候选模型池的组合遍历（不再是全局「账号池 × 模型列表」笛卡尔积）；某账号未配置自有模型池时，回退使用全局共享候选模型列表（向后兼容字段 `model_candidates`，见 REQ-003b 配置说明）
  - 每个候选模型项可单独配置免费时段（未配置视为全天可用，见 REQ-003b）
  - 理由：真实账号的可用模型与免费规则本就随账号而异（如同名模型在 A 账号仅 0:00–8:00 免费、在 B 账号全天免费）；按账号建模让配置与事实一致，也让「组合级时段」这一原二期增强项在一期即可落地
- **[REQ-003a]** 系统应支持**工作空间（工作目录）配置**：
  - 支持管理多个命名工作空间（如「项目 A：E:\proj\a」「项目 B：E:\proj\b」），可增删改
  - 三个层级的空间指定，优先级从高到低：**单任务覆盖 > 本批默认 > 全局默认**；任务文件中的任务项可通过 `workspace` 字段单独指定
  - Agent CLI 子进程在指定工作空间目录下启动执行，界面实时显示当前任务所用工作空间
  - 预检阶段校验：工作空间目录不存在或无访问权限时阻止启动并明确定位到具体空间配置；任务引用的命名空间被重命名/删除导致悬空的，加载阶段报错并定位到具体任务
  - 理由：批处理任务往往面向不同项目目录执行（改代码、生成文档），空间不对则任务结果全部落错位置；多空间 + 三级覆盖是批处理灵活性的基础
- **[REQ-003b]** 系统应支持为「账号下的候选模型项」配置「免费时段」（free time window）：配置了时段的「账号 × 模型」组合仅在指定时段内参与降级矩阵调度，**未配置时段的模型项视为全天可用**（v1.12 修订）
  - 配置粒度：时段按**账号下的模型项**配置——候选模型池挂在账号下（见 REQ-003），同一模型名在不同账号下可配置**不同的**时段（例：A 账号 Hy4 设 0:00–8:00，B 账号 Hy4 设 0:00–24:00）；「组合级时段」原为二期增强候选（v1.10 R-1），v1.12 随候选池挂账号一并落地为一期行为（v1.12 修订）
  - 时段定义：每日起止时间（HH:mm–HH:mm，**支持跨零点**如 22:00–06:00）+ 可选星期过滤（默认周一至周日均生效）；按本机系统时间判定
  - 星期过滤语义：`days` 按**时段覆盖日**判定——时段覆盖的任一日命中 `days` 列表即生效（跨零点时段同时检查开始日与结束日；如工作日 22:00–06:00 场景下，「周日 22:00 → 周一 06:00」因覆盖周一而生效）；配置界面跨零点时段以「周日 22:00 → 周一 06:00」形式预览展示（v1.10 新增，对应评审 R-2）
  - 调度语义：处于时段外的模型在降级/调度决策中被直接跳过——不发起调用、不计入任务失败、不触发模型切换告警；「免费时段外」与「额度耗尽」是两种独立的不可用原因，埋点与报告须区分（见第 11 章、REQ-011）
  - 无可用组合时的行为：若全部组合均处于时段外（或全部组合均处于额度冷却中，见 REQ-004c），且存在「即将恢复可用」的组合、其恢复时间在「最长可等待时长」（默认 60 分钟，可配置）内，则批处理进入 **waiting**（等待下一免费时段 / 额度重置）状态，界面显示倒计时，到点自动继续；否则进入 blocked 并提示下一可用时段开始时间（或最早恢复时间点）
    - 等待目标取所有候选恢复时间点（下一免费时段开始时间、额度重置时间，见 REQ-004c）中最早者；恢复时间相同时按降级矩阵遍历顺序（账号顺序 × 账号内候选顺序）取第一个；单个组合的恢复时间点取其各可用性约束解除时间中的最晚者（如同时处于时段外与冷却中，恢复时间 = max(下一时段开始, 重置时间)）（v1.10 新增，对应评审 R-4；v1.11 扩展至额度冷却；v1.12 修订排序口径）
    - waiting 期间用户补充额度 / 新增账号或模型 / 修改时段配置 / 手动重置组合冷却标记时，系统立即重新评估可用性：若已存在可用组合，提前退出 waiting 继续执行（v1.10 新增，对应评审 R-4；v1.11 扩展）
    - waiting 结束自动继续时，此前被标记 interrupted 的当前任务按续跑逻辑重新执行（以完整指令重新发起，见 REQ-004）（v1.10 新增，对应评审 R-4）
    - 取消等待后批级状态转入 **blocked**，界面提示下一可用时段开始时间，用户可补充额度/账号模型后续跑（v1.10 新增，对应评审 R-4）
  - 在途任务不受时段边界影响：任务已启动执行后，即使时间跨越该模型的时段边界，也不中断、不失败；任务完成后按新时段视图调度下一条
  - 兜底联动：兜底触发条件中的「免费组合矩阵不可用」包含「全部模型处于时段外」的情形（见 REQ-004b）
  - 预检联动：启动时若全部模型处于时段外，提示下一可用时段，并允许用户选择「等待至时段开始自动启动」或「以 blocked 状态退出」（见 REQ-010）
  - 配置示例（账号条目，v1.12 修订）：
    ```json
    {
      "id": "acc-1",
      "credential_ref": "profile:acc-1",
      "model_candidates": [
        { "name": "Hy4", "free_time_window": { "start": "00:00", "end": "08:00" } },
        { "name": "model-b" }
      ],
      "fallback_models": [
        { "name": "paid-model", "estimated_unit_price": 0.5 }
      ]
    }
    ```
    字段说明（v1.12 修订）：`model_candidates` 为**该账号自有**的有序候选模型池，`name` 在账号内唯一（不同账号可出现同名模型但时段/单价独立）；`free_time_window` 缺省或为 null 表示全天可用；`days` 为可选星期过滤（mon–sun），按时段覆盖日判定；`fallback_models` 为该账号自有的有序兜底模型池（不参与免费时段过滤，见 REQ-004b）。账号未配置 `model_candidates` 时回退使用全局共享字段 `model_candidates`（向后兼容）
  - 理由：部分模型的免费额度有固定时段（如每日免费额度仅在特定时段生效、夜间免费等），无时段感知的调度会在非免费时段误用模型，或把「时段外」误判为「额度耗尽」而白白切换/阻塞
- **[REQ-004]** 系统应识别「额度耗尽」类错误（配额用尽/余额不足/持续限流），自动在降级矩阵中切换到下一个可用组合（**默认模型优先**：同账号先轮换**该账号自己的**候选模型池，该账号模型全部耗尽后再切换下一个账号；策略可配置），并从当前任务继续执行。降级矩阵 = 各启用账号与其自有候选模型池的组合遍历（候选模型池挂账号下，见 REQ-003）；设置了免费时段且当前处于时段外的组合不参与调度（见 REQ-003b），处于额度冷却期（重置时间未到）的组合同样不参与调度（见 REQ-004c）（v1.12 修订）
  - 遍历顺序定义（v1.12 修订）：
    - **模型优先（默认）**：按账号池顺序，逐账号遍历其自有候选模型池——账号 1 的模型全部耗尽/不可用 → 账号 2 的模型 → …
    - **账号优先**：按「模型名」聚合遍历——先把同一模型名在所有配置了它的账号上轮完，再换下一个模型名（模型名按各账号候选池中的首次出现顺序）
  - 「从当前任务继续执行」的语义定义为：**以该任务的完整指令重新发起一次全新会话执行，不继承上一次会话的上下文**；上一次执行已产生的磁盘副作用保留在文件系统上，最终结果由任务指令自身的幂等性决定（v1.8 修订，详见第 10 章技术考虑）
  - 理由：本工具的核心差异化价值；多账号接力可显著延长无人值守时长；同账号换模型无需重新登录账号，切换开销更低
- **[REQ-004a]** 系统应支持为批处理指定 WorkBuddy 专家或专家团作为执行者，未指定时使用默认智能体
  - 理由：任务类型多样，专业角色执行质量更高
- **[REQ-004b]** 系统应支持配置「特殊模型兜底」：当当前任务未完成、且免费组合当前不可用（额度耗尽，或全部组合处于免费时段外）时，切换到用户预设的特殊模型（如付费模型）**完成当前这一条任务**（同样以完整指令重新执行）；该任务完成后，后续任务继续按正常降级策略使用下一个免费组合，不再使用特殊模型（v1.12 修订：兜底模型池挂在账号下）
  - **兜底模型池挂账号下**（v1.12 修订）：每个账号可配置自己独立的有序兜底模型池（`accounts[].fallback_models`）；兜底触发时按「账号顺序 × 该账号兜底池顺序」遍历，取第一个可用的兜底组合执行；兜底模型同样不参与免费时段过滤
  - 全局开关与成本上限：兜底总开关（`fallback.enabled`，默认关）与单任务/单批成本上限为**全局配置**，约束所有账号的兜底行为；至少一个启用账号配置了兜底模型时才具备兜底能力
  - 触发条件（同时满足）：① 当前任务未完成（已投入执行、可能已产生部分磁盘产出）；② 免费组合矩阵当前不可用（额度耗尽，全部组合处于免费时段外，或全部组合处于额度冷却中，见 REQ-004c）；③ 兜底功能已开启且未超出成本上限
  - 时段约束：兜底模型**不参与免费时段过滤**——兜底的目的是保证当前任务能收尾，叠加时段约束会在需要时不可用；若用户的特殊模型本身有时段限制，应将其配置为候选模型而非兜底模型（v1.10 新增，对应评审 R-3）
  - 安全约束：默认关闭；必须可配置成本上限（如单任务/单批最大花费，超出即停用兜底转为 blocked）；兜底使用量单独记录并在报告中列示
  - 用量数据来源：兜底触发判定与花费记录依赖 CLI 返回的 token 用量/费用数据（M0 V-7 验证）；**若 V-7 结论为不可得，降级方案为「按调用次数 × 模型预估单价」粗控成本上限，报告中花费列示为估算值并标注口径**
  - 理由：免费组合间切换意味着当前任务要以完整指令重新执行；免费组合当前不可用时，若不兜底，任务只能推迟到 blocked / waiting 等待额度恢复或下一免费时段，已投入的时间被浪费；兜底模型保证断点任务能在本次运行内收尾，是可选保险而非强制
- **[REQ-004c]** 系统应在「账号 × 模型」组合发生额度耗尽时记录该组合的**额度重置时间点**（quota reset time），并在重置时间前将其标记为**冷却中（cooldown）**——冷却中的组合不参与降级矩阵调度、不发起调用、不计入重试尝试，从源头减少不必要的重试
  - 数据来源（按优先级）：① 解析 CLI 返回的额度耗尽错误中的重置时间信息（ISO 8601 时间戳 / 相对时长如 "3h24m" / HTTP `Retry-After` 头等，由适配层归一化；各 CLI 实际格式由 M0 V-10 验证）；② 解析失败时降级为「默认冷却时长」（可配置，默认 60 分钟，标注为假设），自错误发生时刻起算，数据来源标注为「默认冷却」
  - 持久化：冷却记录（账号 × 模型 → 重置时间点 + 数据来源）随运行日志落盘；工具重启后冷却记录仍然有效，防止重启后立刻对同一组合发起注定失败的调用
  - 恢复语义：到达重置时间点后组合自动恢复参与调度；恢复后若再次额度耗尽，以新解析出的重置时间覆盖旧记录
  - 恢复时间点计算：组合可用需同时满足「不在额度冷却期」与「在免费时段内（如该模型配置了时段）」；组合的恢复时间点取各约束解除时间中的**最晚者**（重置时间与下一时段开始时间取 max）
  - 全组合冷却时的行为：若所有组合均在冷却中，按最早恢复时间点复用 REQ-003b 的 waiting 机制——最早恢复时间在「最长可等待时长」（默认 60 分钟，可配置）内则批处理进入 waiting 倒计时等待（等待目标规则见 REQ-003b），否则进入 blocked 并提示最早恢复时间点
  - 预检联动：启动时若全部组合均处于冷却中，提示最早恢复时间点，允许用户选择「等待至最早恢复时间自动启动」（进入 waiting）或「以 blocked 状态退出」（同 REQ-010）
  - 与兜底的联动：兜底触发条件中的「免费组合矩阵当前不可用」包含「全部组合处于额度冷却中」的情形（见 REQ-004b）
  - 与免费时段的关系：额度冷却（额度维度）与免费时段（时间维度）是两个独立的可用性约束；两类跳过均为预期调度行为——不计失败、不触发切换告警、不污染误切换率，但埋点与报告须区分（model_window_skipped vs model_cooldown_skipped，见第 11 章 / REQ-011）
  - 与重试上限的关系：冷却中的组合不计入 REQ-009a 的总尝试次数（不发起调用即不消耗尝试），有限的重试额度只投向可能成功的调用
  - 埋点：记录 quota_reset_recorded 事件（账号、模型、重置时间点、数据来源），见第 11 章
  - 理由：额度耗尽后组合在重置前必然不可用；若无重置时间感知，调度器会在矩阵中反复命中已耗尽组合，白白消耗重试尝试与切换开销，甚至过早进入 blocked。记录重置时间点让调度器「知道何时值得再试」，显著减少无谓重试，并支撑全组合冷却时按最早恢复点自动等待，延长无人值守时长
- **[REQ-005]** 系统应区分「临时限流」与「额度耗尽」：临时限流先退避重试（默认 3 次，间隔递增），重试耗尽后才升级为切换
  - 与 REQ-004c 联动：判定为「额度耗尽」时记录该组合的重置时间并进入冷却；「临时限流」不记录冷却（按退避重试同一模型）（v1.11 新增）
  - 理由：避免误切换浪费候选模型
- **[REQ-006]** 每条任务完成后应立即将结果原子写回任务文件（临时文件 + 替换），包含：状态、结果、实际使用模型、实际使用账号、执行专家、耗时、时间戳、重试次数、兜底标记与花费（如有）
  - 实现要求：每次启动前自动备份任务文件（`<任务文件名>.backup-<时间戳>`，默认保留最近 5 份），防止结果单点存储
  - 理由：崩溃安全与断点续跑的基础
- **[REQ-007]** 系统应提供实时界面：总进度、各任务状态计数（pending/running/done/failed/interrupted）与批级状态、当前任务/账号/模型/工作空间/执行专家、单任务详情（指令 + 流式输出 + 结果）
  - 理由：用户对执行过程必须有可见性与掌控感
- **[REQ-008]** 用户应能随时终止批处理：当前任务安全中断、状态落盘、子进程回收；并能从断点续跑（默认跳过已完成任务）
  - 续跑支持「强制重跑」开关：开启后忽略已完成状态，重跑全部任务或用户在界面勾选的任务子集
  - 续跑重跑 interrupted 任务时，该任务旧的「部分输出」被清除，由本次运行的新结果替换（旧输出保留在运行日志中供追溯）（v1.10 新增，对应评审 R-10）
  - 理由：核心控制权诉求；强制重跑是断点续跑语义的必要补充（任务描述修正后需要重跑）
- **[REQ-009]** 单任务失败应按重试策略处理（默认重试 2 次），仍失败则标记 failed 并继续后续任务
  - 理由：单点失败不能阻塞整批
- **[REQ-009a]** 系统应对单任务设置**总尝试次数上限**（默认 10 次，含各类重试与降级切换后的重试）与**总时长上限**（默认 60 分钟，含全部重试、退避等待与切换），二者均可配置；超限的任务标记 failed（错误信息注明超限类型），不阻塞整批
  - 冷却豁免：处于额度冷却期的组合不计入总尝试次数（不发起调用即不消耗尝试，见 REQ-004c）（v1.11 新增）
  - 理由：防止重试策略叠加（临时限流 3 次 × 普通重试 2 次 × 降级组合数）导致单任务运行数小时并拖住整批
- **[REQ-010]** 启动前应预检 Agent CLI 可用性（已安装、已认证）、任务文件合法性与账号池可用性
  - 账号池预检：对每个启用账号做一次极简调用校验，失效账号（过期/未登录）自动标记停用并在界面提示，不等到执行时才暴露
  - 预检范围包含：本批及各任务指定的工作空间目录存在且可访问（见 REQ-003a）、指定专家/专家团可用（见 REQ-004a）、候选模型免费时段可用性评估：若启动时全部候选模型均处于时段外，提示「当前无可用模型」并显示下一可用时段开始时间与倒计时，由用户选择「等待至时段开始自动启动」（进入 waiting 批级状态，与运行中等待同语义，见第 10 章）或「以 blocked 状态退出」（见 REQ-003b）、组合额度冷却状态评估：若启动时全部组合均处于冷却中（见 REQ-004c），提示最早恢复时间点，由用户选择「等待至最早恢复时间自动启动」（进入 waiting）或「以 blocked 状态退出」
  - 理由：快速失败，避免跑一半才发现环境问题
- **[REQ-010b]** 系统应记录自动应答行为：凡自动选择了默认选项的交互点，应写入运行日志（交互内容 + 默认选项）；其中高危确认点（命中 REQ-002b 黑名单或白名单边缘）应醒目标记
  - 理由：自动默认可能不总是用户想要的（如权限确认），日志可事后追溯与调整

### 应该有 (P1) - 重要但不阻断

- **[REQ-011]** 批处理结束生成汇总报告（成败统计、账号/模型使用量与切换时间线、兜底模型与花费统计、失败清单）
  - 使用量口径：若 M0 V-7 验证 CLI 返回 token/费用数据，按实际值列示；否则按调用次数列示并标注「估算」
  - 切换事件的原因须区分「额度耗尽 / 临时限流 / 免费时段外跳过 / 额度冷却跳过」：时段外跳过与额度冷却跳过均属预期调度行为，不计入误切换率指标；报告另统计「时段外累计等待时长」与「额度冷却累计等待时长」（v1.11 修订）
  - 理由：批量任务的可追溯性
- **[REQ-012]** 支持受控并发（可配置并发数，默认 1 即串行）。并发设计约束（P1 实现前必须落实）：
  - 额度与冷却状态共享：并发任务共享「账号池 × 模型」可用性视图（含免费时段可用性与额度冷却状态，见 REQ-003b/004c），某任务触发额度耗尽或时段边界后，该组合（含其重置时间记录）对所有并发任务实时标记为不可用
  - 单写者：任务文件回写统一由调度线程串行执行，内存状态为唯一事实来源，避免并发写冲突
  - 界面口径：「当前任务」展示全部 running 任务卡片，「当前账号/模型」按任务分别展示
  - 终止顺序：先停止派发新任务 → 逐一回收 Agent 子进程 → 全部落盘 → 反馈已终止
  - 理由：部分场景可提速；但一期默认串行，降低复杂度
- **[REQ-013]** 支持「失败即停」开关（默认关）：开启后单任务最终失败即暂停整批并提示，用户确认后继续或终止
  - 理由：不同任务性质需要不同容错策略（强制重跑已升为 P0 并入 REQ-008）
- **[REQ-014]** 模型切换事件与任务执行日志持久化到运行日志文件
  - 理由：排查问题需要
- **[REQ-015]** 支持配置「批处理结束后自动关机」
  - 触发条件（默认行为显式定义）：批处理**正常完成** = 全部任务到达终态（done/failed/interrupted 均有明确记录）且无 blocked / waiting 等未完结运行态；**默认允许带 failed 任务关机**（failed 已具备归因与日志）；仅当用户勾选「仅当失败率为 0 时关机」时，存在 failed 才阻止关机
  - 被用户终止、进入 blocked、或失败率条件不满足时，不触发并在界面与报告标注原因
  - 安全约束（必须全部满足）：
    - 默认关闭，需在配置页显式开启，并弹出二次确认（说明后果与取消方式）
    - 触发前有**可撤销倒计时**（默认 60 秒），期间界面提供「取消关机」按钮，可随时中止
    - 关机前确保所有结果已落盘、子进程已回收
  - 跨平台实现：Windows 使用关机命令（如 `shutdown`，需当前用户具备关机权限）；macOS 使用 AppleScript 触发关机（可能要求管理员授权）；权限不足时不执行关机，降级为「提示手动关机」并记录原因（与第 8 章兼容性对应）
  - 理由：长时间无人值守批处理（如过夜跑任务）结束后自动关机，省电省心；因属破坏性系统操作，撤销窗口与触发条件约束不可省略

### 可以有 (P2) - 未来增强

  - 理由：锦上添花，二期可并入工作流编排

  - 理由：提升结果审阅效率

  - 理由：长时间无人值守场景的补充

## 8. 非功能需求

### 性能

- 界面状态刷新延迟 ≤ 2 秒
- 单条任务结果回写 ≤ 1 秒（不含 Agent 执行时间）
- 支持任务文件规模：单批 ≥ 1000 条任务（串行执行时内存占用平稳）
- 规模预期说明：1000 条为**规模上限保障**而非典型场景；典型单批 20–100 条。串行 + 默认 10 分钟单任务超时下，1000 条理论最长运行约 7 天——超大批次建议拆分为多批或启用受控并发（P1）；结果文件随任务量全量增长，建议设单任务结果大小上限（默认 100KB，超出截断并在任务详情中提示全量日志位置）

### 可靠性

- 任务文件写入 100% 原子性，强杀/断电不损坏文件
- 每次启动前自动备份任务文件（保留最近 5 份），对应反向指标「结果文件损坏次数 = 0」
- 断点续跑 100% 保留已完成结果
- Agent CLI 子进程在终止/崩溃后无残留

### 安全

- API 凭证/登录态仅本地保存，不写入任务文件与日志明文
- 任务结果中如含敏感信息，用户自行管控任务文件权限（工具不做加密，一期范围外，见第 3 章）
- 自动应答的危险操作防护见 REQ-002b；高危确认点在日志中醒目标记（REQ-010b）
- 多账号接力仅限用户自有合法账号的免费额度，用户自行承担平台账号使用规范责任（对应第 14 章风险表）（v1.10 新增，对应评审 R-6）

### 兼容性

- 操作系统：Windows（优先，当前环境）、macOS（视需要）
- 运行依赖：Node.js 或 Python（与所选 Agent CLI 调用方式匹配，技术选型待定）
- 自动关机功能依赖系统关机命令与相应权限（Windows 需关机权限；macOS 可能需管理员授权），权限不足时降级为提示手动关机（见 REQ-015）

### 易用性

- 从「拿到任务文件」到「开始执行」的操作步骤 ≤ 3 步
- 界面提供空状态、运行中、等待时段、终止、阻塞（额度全尽或时段外且无可等待时段）、完成 六种关键状态

## 9. 用户体验与设计

### 关键页面

1. **配置页**：选择任务文件、选择执行工具（WorkBuddy/CodeBuddy）、管理工作空间（多空间增删改，设置全局默认与本批默认空间）、管理账号池（多账号增删/排序/启停，**每个账号内编排自己独立的候选模型池与免费时段**（见 REQ-003/003b）及兜底模型池（见 REQ-004b）；全局兼容字段：共享候选模型列表）、选择执行专家/专家团、配置兜底全局开关与成本上限（单任务/单批总上限，默认关）、配置危险操作白名单（REQ-002b）、设置并发/重试/超时/单任务总上限（REQ-009a）/降级策略（默认模型优先，可切账号优先）、可选「完成后自动关机」（默认允许带 failed 关机；可选「仅失败率为 0 时关机」；含二次确认与跨平台权限提示）。配置页承载配置域较多，采用分组布局或分步向导组织以降低认知负担（具体交互方案随技术选型确定，见第 16 章）；跨零点免费时段在配置界面以「周日 22:00 → 周一 06:00」形式预览展示（见 REQ-003b）（v1.12 修订：模型池配置入口移入账号管理）
2. **执行监控页**（主页面）：顶部总进度条 + 状态统计卡（任务级计数 + 批级状态 + 已跳过计数）；中部任务列表（状态徽标：待处理/执行中/完成/失败/已中断）；底部当前任务实时输出流
3. **报告页**：批处理结束后的汇总视图

### 设计原则

1. **状态一目了然**：3 秒内看懂「跑到哪了、用哪个账号模型、有没有出问题」
2. **随时可停、停了可续**：终止与续跑是最显眼的两个操作
3. **异常可解释**：任何失败/切换都附带人话版原因，不裸抛错误码

### 需要设计的状态

- [x] 空状态（未选任务文件）
- [x] 运行中（含模型/账号切换 toast 提示、兜底使用标识）

- [x] 终止状态（可续跑）
- [x] 完成状态（含失败清单入口）

## 10. 技术考虑

**注意：** 以下为高层方向，非技术规格，最终方案由技术评审确定。

### 架构方法

- **调度引擎（本地进程）**：任务解析 → 队列调度 → Agent CLI 子进程调用 → 结果回写，单机本地运行
- **Agent 调用层**：通过 WorkBuddy / CodeBuddy 的 CLI 无头模式（headless / 非交互参数）执行任务指令，捕获 stdout/退出码作为结果；每家 CLI 一个 adapter
- **状态存储**：任务文件本身即状态源（status 字段落盘），辅以运行日志文件；Markdown 格式的状态源为 sidecar 结果文件
- **界面**：本地 Web UI（引擎起本地服务 + 浏览器访问）或轻量桌面壳；引擎与界面通过轮询/SSE 通信

### 关键技术决策（待工程评审）

1. **额度耗尽的判定方式**：依赖错误码/错误消息模式匹配（各 CLI 的额度错误特征需逐一摸底），误判率是关键风险
   - 权衡：模式匹配简单但脆弱；预留「手动标记额度耗尽」的兜底入口
2. **续跑语义与幂等性（v1.8 修订，对应评审 B-1）**：
   - 批级「断点续跑」= 以任务文件中 status 字段为准（done 不重跑），任务需有稳定 ID（规则见 REQ-001a）
   - 任务级「切换/兜底后继续当前任务」= **以该任务的完整指令重新发起一次全新会话执行，不继承上一次会话的上下文**；已产生的磁盘副作用保留，最终结果由指令幂等性决定
   - 一期按上述「方案 a」实现；M0 V-8 验证 CLI 是否支持会话恢复（session/resume），若支持，二期评估升级为「断点任务恢复」（见第 3 章范围外与第 16 章待解决问题）
3. **用量/费用数据来源（v1.8 新增，对应评审 B-2）**：成本上限与使用量统计依赖 CLI 无头输出中的 token 用量/费用数据；M0 V-7 验证其可得性与返回结构；若不可得，降级为「调用次数 × 预估单价」估算口径（见 REQ-004b/011）
4. **实时输出流**：子进程 stdout 增量转发到界面（SSE/WebSocket）
5. **额度重置时间的获取（v1.11 新增）**：解析 CLI 额度耗尽错误中的重置时间信息（ISO 8601 时间戳 / 相对时长 / HTTP `Retry-After`，由适配层归一化）；M0 V-10 验证各 CLI 的可得性与格式；不可得时降级为可配置的「默认冷却时长」（见 REQ-004c）

### 数据模型（任务项）

| 字段                                             | 说明                                                                              |
| ---------------------------------------------- | ------------------------------------------------------------------------------- |
| id                                             | 任务唯一标识（稳定，续跑依赖；生成与校验规则见 REQ-001a）                                               |
| workspace                                      | 工作空间（可选，覆盖本批默认；指向命名空间或目录路径）                                                     |
| instruction                                    | 任务指令（发给 Agent 的内容）                                                              |
| status                                         | 任务级状态：pending / running / done / failed / interrupted                           |
| result                                         | Agent 处理结果（部分完成时在结果前标注「部分输出」；interrupted 任务续跑重跑时旧部分输出被清除替换，旧值保留在运行日志，见 REQ-008） |
| model_used                                     | 实际使用的模型                                                                         |
| account_used                                   | 实际使用的账号                                                                         |
| expert_used                                    | 执行的专家/专家团（未指定则为默认）                                                              |
| fallback_used                                  | 是否使用兜底模型完成（true/false）                                                          |
| fallback_cost                                  | 兜底实际花费（实测值或估算值，报告中标注口径）                                                         |
| retry_count                                    | 已重试次数（含降级切换后的重试）                                                                |
| error                                          | 错误信息（失败时）                                                                       |
| started_at / finished_at / duration            | 时间元数据（duration 单位为秒，v1.10 修订，对应评审 R-10）                                         |
| workflow / depends_on / max_loops / batch_size | 二期预留字段：一期不实现、不写入任务文件，仅保证数据模型可扩展（见第 15 章）（v1.10 新增，对应评审 R-8）                     |

**批级状态**（运行态，记录于运行日志，不落任务文件）：idle / running / blocked / terminated / completed / waiting（等待下一可用恢复时间点——下一免费时段开始或额度重置；**独立批级状态**——启动前预检等待与运行中等待均计入 waiting，不是 running 的子状态，见 REQ-003b/REQ-004c/REQ-010）（v1.10 修订，对应评审 R-4；v1.11 扩展）。  
「跳过已完成任务」是续跑时的运行行为（显示跳过计数），不构成任务级状态。  
组合级冷却记录（账号 × 模型 → 重置时间点、数据来源）属运行态，随运行日志落盘、重启后有效，不写入任务文件（见 REQ-004c）。

## 15. 专用场景模板库与二期展望

**定位：** 二期将一期「单条指令批处理」升级为「按软件工程流程完整完成任务」。专用场景模板库是二期的主体交付物之一：把高频软件开发流程沉淀为开箱即用的工作流模板。一期范围外边界见第 3 章。

### 15.1 通用能力原语

场景模板由以下可复用原语组合而成（与二期「流程模板/多阶段编排」能力对应）：

| 原语                           | 说明                                                          |
| ---------------------------- | ----------------------------------------------------------- |
| **审查-修订循环（Review-Fix Loop）** | 生成 → 审查 → 修订 → 再审查，直至审查通过；**最大循环次数可配置**，超限则标记「未通过」并输出遗留问题清单 |
| **分批推进（Batching）**           | 将大集合（模块/文件/用例）切分为批次，逐批处理，每批完成即落盘                            |
| **独立会话（Fresh Session）**      | 每个任务/子任务使用独立会话执行，避免上下文膨胀——**省 tokens、防串扰**                  |
| **质量门禁（Gate）**               | 阶段间卡点：测试通过 / lint 通过 / 审查通过才进入下一阶段；未通过触发修复循环（次数上限）          |
| **人工卡点（可选）**                 | 关键节点可配置为「人工确认」或「自动通过默认选项」（遵循一期 REQ-002a，危险操作除外）             |

### 15.2 用户提出的核心场景（S1–S6）

| 编号 | 场景                  | 流程                                      | 循环/停止条件                        | 关键配置                          |
| -- | ------------------- | --------------------------------------- | ------------------------------ | ----------------------------- |
| S1 | **需求文档生成与审查**       | 生成需求文档 → 审查需求 → 修订 → 再审查                | 循环至审查通过；**最大循环次数可设**           | 审查角色（专家）、通过标准 checklist、最大循环数 |
| S2 | **设计文档生成与审查**       | 生成设计文档 → 审查 → 修订 → 再审查                  | 同 S1，循环至通过；最大循环次数可设            | 设计规范引用、审查维度（架构/可行性/成本）        |
| S3 | **自动排期与逐任务推进**      | 根据需求和设计生成排期（任务拆解+WBS）→ 按排期逐步推进每个任务      | 每个任务独立会话执行（省 tokens）；依赖顺序由排期决定 | 拆解粒度、每任务会话隔离开关、推进节奏（连续/每日）    |
| S4 | **批量代码审查与分批修复**     | 按模块分批审查代码（输出问题清单）→ 问题分级 → 分批修复 → 复审     | 分批推进；修复后复审未通过项进入修复循环           | 批大小、问题严重度过滤、最大修复轮数            |
| S5 | **批量端到端（E2E）测试与修复** | 分批编写/执行 E2E 用例 → 汇总失败用例 → 定位修复 → 重跑失败用例 | 分批推进；修复后仅重跑失败项（省 tokens）       | 用例批大小、失败重跑策略、最大修复轮数           |
| S6 | **批量可用性测试与修复**      | 分批执行可用性检查（走查/启发式评估）→ 输出问题清单 → 修复 → 复检   | 分批推进；复检通过即止                    | 评估维度（WCAG/交互/文案）、批大小、最大循环数    |

**S1/S2 的通用性说明：** 「生成→审查→修订直至通过」循环可复用于任何文档类型（测试方案、运维手册、调研报告等），S1/S2 只是参数化实例。

### 15.3 补充场景（S7–S16，由产品侧补充，供评审取舍）

| 编号  | 场景               | 流程                                             | 循环/停止条件               |
| --- | ---------------- | ---------------------------------------------- | --------------------- |

| S10 | **代码规范批量整改**     | lint/format 扫描 → 问题分级 → 分批自动修复 → 复扫清零          | 违规数 = 0 或达到可接受阈值      |

| S12 | **性能问题批量优化**     | profiling 报告 → 热点分级 → 分批优化 → 基准测试对比            | 达到性能目标或收益低于阈值即止       |

| S15 | **发布流水线**        | 版本号更新 → changelog 生成 → 发布说明 → 回归清单生成 → 发布检查    | 各步 Gate 通过即发布；任一步失败阻断 |

**模板库机制：** 每个场景模板 = 阶段序列 + 原语组合 + 默认参数（批大小/循环上限/门禁标准），用户可基于模板微调参数后启动，也可保存为自定义模板。

### 15.4 二期方向

1. **流程模板**：将任务从「单条指令」升级为「工作流」，内置软件工程阶段模板：需求澄清 → 方案设计 → 编码 → 自测 → 代码审查 → 交付物输出
2. **多阶段编排**：每个任务按流程节点依次执行，上一阶段产出作为下一阶段输入；支持人工卡点（如设计确认后再编码）
3. **项目级任务**：任务对象从「一条指令」升级为「一个需求项」，可关联代码仓库、产出分支/PR
4. **质量门禁**：编码类任务自动触发测试/lint，未通过自动修复循环（有次数上限）
5. **任务依赖**：支持任务间依赖关系（DAG），按依赖拓扑调度（S3 排期推进的基础）
6. **断点任务恢复与会话继承**：若 M0 V-8 验证 CLI 支持会话恢复，将「切换后继续当前任务」从「重新执行完整指令」升级为「恢复上次会话」
7. **Markdown 任务文件原地回写**：补全 Markdown 格式的状态/结果回写规范（一期为 sidecar 策略）
8. ~~**组合级免费时段配置**~~：**已在一期落地（v1.12）**——候选模型池挂账号下后，免费时段天然按「账号 × 模型」组合配置（见 REQ-003/003b），本项不再作为二期内容（v1.10 新增对应评审 R-1，v1.12 关闭）

**一期为二期预留的接口：**

## 18. 附录

### A. 任务文件格式

**JSON 格式（原地原子回写）：**

```json
[
  {
    "id": "task-001",
    "workspace": "proj-a",
    "instruction": "将 src/utils.ts 中所有函数补充 JSDoc 注释",
    "status": "pending",
    "result": "",
    "model_used": "",
    "account_used": "",
    "expert_used": "",
    "fallback_used": false,
    "fallback_cost": null,
    "retry_count": 0,
    "error": "",
    "started_at": "",
    "finished_at": "",
    "duration": 0
  }
]
```

**workspace 字段说明：** 可省略（使用本批默认/全局默认空间）；可填命名空间名（如 `proj-a`）或直接填目录路径。

**字段口径说明（v1.10 新增，对应评审 R-8/R-10）：** `duration` 单位为秒；`fallback_cost` 为兜底实际花费（实测值或估算值，口径见 REQ-004b）。二期预留字段（`workflow` / `depends_on` / `max_loops` / `batch_size`）一期不实现，故未列入本示例（见第 10 章数据模型与第 15 章）。

**Markdown 格式（只读输入，v1.8 定稿）：**

```markdown
# Tasks

## task-001
- instruction: 将 src/utils.ts 中所有函数补充 JSDoc 注释

## task-002
- instruction: 为 src/parser.ts 补充单元测试

## task-003
- instruction: 修复登录模块缺陷：
  1. 定位 src/auth/login.ts 的空指针风险并修复
  2. 补充回归用例
```

**指令多行界定规则（v1.10 新增，对应评审 R-9）：** `- instruction:` 行的内容可跨多行——自指令行起至下一个二级标题（或文件结尾）之间的全部内容（含缩进列表、代码块等）合并为该任务的完整指令；该区间内的其余内容不单独作为元数据解析。

**Markdown 回写策略（v1.8 修订，对应评审 M-6）：**

- Markdown 文件为**只读输入源**，工具不修改用户原文（用户可能在任务区写代码块、多级列表，回写易破坏排版）
- 执行状态与结果写入同目录 sidecar 文件：`tasks.md` → `tasks.md.result.json`，结构与 JSON 任务文件一致（含全部回写字段）
- 续跑以 sidecar 为准：sidecar 中已 done 的任务 ID 默认跳过；sidecar 不存在时首次运行自动生成（全部 pending）
- Markdown 原地回写规范列入二期（第 15 章）

### B. 额度降级状态机（账号池 × 模型候选 双维度）

```
执行中(账号1 + 模型A) ──临时限流──▶ 退避重试×3 ──仍失败──▶ 降级判定
        │                                              │
        └──额度耗尽────────────────────────────────────▶ ▼
              ① 先过滤免费时段：设置时段且当前时段外的模型直接跳过（REQ-003b）
                              默认策略（模型优先，v1.12：模型池挂账号下）：
                              账号1+模型A耗尽 → 账号1+模型B → … → 账号1+模型N（账号1自有候选池全耗尽）
                              → 账号2+其自有首选模型 → … 遍历「各账号 × 自有候选池」组合矩阵
                                       │
                        矩阵内仍有可用组合 ──▶ 切换组合，当前任务以完整指令重新执行
                        矩阵当前无可用组合 ──▶ 判断：当前任务未完成 & 兜底已开启 & 未超成本上限
                                            ├─ 是 ──▶ 特殊模型兜底（同样以完整指令重新执行当前任务）
                                            │          └─ 完成后回到正常降级（下一个免费组合）
                                            └─ 否 ──▶ 判断：是否存在「即将进入免费时段」的模型，
                                                      且开始时间在最长可等待时长内
                                                      ├─ 是 ──▶ waiting（等待至下一恢复时间点：
                                                      │          时段开始或额度重置，界面倒计时，
                                                      │          可取消（取消转 blocked），到点自动继续；
                                                      │          配置变更即重新评估）
                                                      └─ 否 ──▶ blocked(暂停，可续跑；已产出部分结果保留)
```

**语义说明（v1.8 修订，对应评审 B-1）：** 切换组合或兜底后的「继续当前任务」= 以该任务的完整指令重新发起一次全新会话，**不继承上次会话上下文**；上次执行已产生的磁盘副作用保留，最终结果由指令幂等性决定。若 M0 V-8 验证 CLI 支持会话恢复，二期升级为断点任务恢复。

**时段语义说明（v1.9 新增，v1.10 补全，对应评审 R-2/R-4；v1.12 修订粒度）：** 「免费时段外跳过」与「额度耗尽」是两种独立的不可用原因——前者是预期调度行为（不调用、不计失败、不告警），后者是异常事件（触发切换与告警）；二者在埋点、切换事件与报告中须区分（见第 11 章、REQ-011）。时段判定以本机挂钟时间为准，跨零点时段（22:00–06:00）视为连续区间；`days` 按**时段覆盖日**判定（覆盖任一日命中即生效）。时段按「账号下的模型项」配置——同一模型在不同账号下可配不同时段（见 REQ-003/003b，v1.12）。waiting 规则：等待目标取最早恢复的组合（并列按降级矩阵遍历顺序：账号顺序 × 账号内候选顺序）；等待期间配置变更即重新评估，已可用则提前退出；取消等待转入 blocked；waiting 恢复后 interrupted 任务按续跑逻辑重跑。

**降级策略可配置：** `模型优先`（默认，同账号先轮完**其自有**候选模型池，再换下一个账号）或 `账号优先`（先把同一模型名在所有配置了它的账号上轮完，再换下一个模型名，模型名按首次出现顺序）（v1.12 修订）。

**兜底模型池（v1.12 修订）：** 每个账号可配置自己独立的有序兜底模型池（`accounts[].fallback_models`），兜底触发时按「账号顺序 × 该账号兜底池顺序」选取第一个可用兜底组合；兜底总开关与成本上限为全局配置。

**专家/专家团：** 独立于降级维度——专家是「谁来做」，账号/模型是「用什么资源做」，降级切换时专家配置保持不变。
