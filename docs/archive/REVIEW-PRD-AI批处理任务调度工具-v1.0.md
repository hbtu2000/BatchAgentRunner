## 1. 审查结论

**总体评级：B+（良好，有条件通过）**

本文档是一份质量明显高于平均水平的个人工具 PRD：问题—目标—指标链路完整，用例与用户故事覆盖主流程与主要边缘情况，安全设计意识突出（自动关机的三重约束、兜底默认关闭 + 双成本上限、自动应答日志），M0 技术验证与阻断项前置识别清晰，变更日志维护习惯良好。

## 2. 值得保持的亮点

1. **问题—目标—指标闭环**：基线 → 目标 → 时间表 → 优先级五列指标表，且设了反向指标（重复执行率、文件损坏次数），这在个人工具 PRD 中少见地专业。

## 3. 🔴 阻塞级问题（Must Fix）

### B-1 「断点续跑 / 任务从断点继续」的核心语义从未定义

- **位置：** 用例 2（L122）、故事 2.2（L212）、REQ-004（L370）、REQ-004b（L376）、风险表（L589）
- **问题：** 文档反复使用「任务从该条继续」「而非从头重跑整批」「换账号重跑会导致上下文丢失」等表述，暗示任务执行存在可保留、可恢复的**上下文/会话状态**。但 PRD 从未定义：
  - Agent CLI 无头调用每次都是新进程，切换账号/模型后重试当前任务时，是**重新执行完整指令**，还是**恢复上次会话**？
  - 若是重新执行完整指令，则「上下文丢失」这一兜底核心理由（L376）不成立——本来就没有上下文；
  - 若支持会话恢复，则需要新增需求：中间产出/会话 ID 的保存方式、恢复时如何注入，且必须列入 M0 验证 CLI 是否支持 session/resume 参数。
- **影响：** 这是 adapter 层设计、兜底价值主张、「上下文丢失」风险是否真实存在 three 者的共同地基。当前状态下，工程实现必然与产品意图出现偏差。
- **建议：** 二选一并全文统一表述：
  - **方案 a（推荐，一期）**：明确定义为「重新执行该任务的完整指令，此前产出不继承」，同步删除/改写所有「上下文丢失」表述，REQ-004b 的理由改为「避免重复消耗已投入的额度与时间」；
  - **方案 b**：若 CLI 支持会话恢复，新增 REQ 定义会话状态的保存与恢复，并列入 M0。

### B-2 兜底成本上限无法执行——CLI 是否返回用量/费用数据未知

- **位置：** REQ-004b（L373-376）、REQ-011（L405）、故事 2.5（L301）
- **问题：** REQ-004b 要求兜底「未超出成本上限」时才能触发、并「记录实际花费」；REQ-011 要求报告包含「各模型使用量」。这两个需求的技术前提是**每次 CLI 调用能获得 token 用量/费用数据**。但全文（含第 12 章阻断项、第 15 章待解决问题）均未验证 WorkBuddy/CodeBuddy 无头输出是否包含计费/用量信息。
- **影响：** 若 CLI 不返回用量，「成本上限」无法在线执行、「使用量统计」无法生成，兜底的两大安全约束（双上限、花费列示）形同虚设——而这正是该功能被设为 P0 的理由。
- **建议：** 列入 M0 验证清单（见第 7 节 V-7）；若不可得，降级方案为「按调用次数 + 估算 token 粗控 + 仅事后统计」，并在 PRD 中明示降级路径。

### B-3 REQ-002a 自动选择默认选项缺少危险操作防护，且未入风险登记册

- **位置：** REQ-002a（L356-358）、边缘情况 5（L320-322）、第 13 章风险表（L582-594）
- **问题：** 「任何交互式询问自动选择默认选项」包含**权限确认**场景。若 CLI 对危险操作（删文件、改系统配置、git push/force 等）的默认选项是「允许」，无人值守批处理会把单次误操作放大为整批破坏。风险表登记了 9 条风险，唯独漏掉这条与「零人工介入」直接伴生的风险。
- **影响：** 安全缺口。个人工具同样可能造成不可逆损失（批量改代码场景下尤甚）。
- **建议：** ① 风险表新增「自动批准权限导致破坏性操作」风险（可能性中/影响高）；② 补充缓解措施：危险命令模式黑名单（命中即中断该任务转 failed 或 blocked）、可配置「自动允许范围」白名单；③ REQ-010b 日志对高危确认点增加醒目标记。

### B-4 任务 ID 生成与缺失处理规则未定义（续跑幂等的地基）

- **位置：** 数据模型 id 字段（L519）、技术决策 2（L512）、附录 A（L702-724）
- **问题：** 文档明确「任务需有稳定 ID」「续跑依赖 ID」，但 ID 完全由用户在任务文件中手写，以下规则全部缺失：
  - 用户未写 ID 怎么办（自动生成？报错？）
  - ID 重复、含特殊字符如何处理
  - 用户手动改 ID / 重排文件后，续跑时新旧 ID 对不上会发生什么（已完成的任务会被当作新任务重跑，直接违反「重复执行率 ≤ 1%」反向指标）
- **影响：** ID 是断点续跑和幂等性的唯一依据，规则缺失等于地基缺失。
- **建议：** 新增 REQ：① ID 缺省时按序号自动生成并回写文件；② 重复 ID 在加载时报错并定位；③ 启动时记录 ID 集合，续跑时对「已 done 的 ID 消失/变更」给出明确提示。

## 4. 🟠 重要问题（Should Fix）

### M-1 文档版本元信息不一致
头部「版本：1.0、最后更新：2026-10-14」（L10-11）与变更日志 7 次修订至 v1.7（L750-761）矛盾。评审前应更正为 **v1.7**，否则各方引用版本混乱。

### M-2 缺少「范围外（Out of Scope）」专章
风险表（L593）的缓解措施写「二期边界严格写入范围外」，但全文没有这一章节。应新增并明确列出：一期**不做**工作流编排/DAG、场景模板库（S1–S16）、结果加密、云端同步、diff 视图、通知、桌面壳（若选本地 Web UI）等。这是防止范围蔓延的关键锚点，也是风险表缓解措施能落地的前提。

### M-3 优先级归属冲突：强制重跑 / 失败即停
- 故事 1.1（P0）验收标准包含「强制重跑开关」（L160），但 REQ-013 将「强制重跑 + 失败即停」列为 **P1**（L411-413）；「失败即停」在边缘情况 3（L315）出现但未标优先级。
- 同一功能两个优先级，MVP 范围界定会出现争议。建议二选一：若 MVP 自用必需则升为 P0 并改 REQ-013；否则从故事 1.1 验收标准中移除。

### M-4 任务状态枚举不一致（三层混用）
- 用例 1 期望行为出现「已跳过」状态（L116），但数据模型（L522）与 REQ-007 状态计数（L228）均无 `skipped`；
- `blocked` 在数据模型中是**任务级** status，但在故事 2.2（L213）、边缘情况 8（L299/L333）中是**批级**状态（批处理暂停）；
- 建议分层定义：批级状态（idle/running/blocked/terminated/completed）与任务级状态（pending/running/done/failed/interrupted，+可选 skipped），全文统一。

### M-5 回写字段清单不完整
REQ-006（L384）与故事 1.3（L185）的回写字段为「状态、结果、模型、耗时、时间戳」，**未含 account_used**；但故事 2.2/2.3（L214/L272）与用例 2 明确要求记录实际使用的账号，数据模型也有该字段（L525）。REQ-006 应补齐 account_used / expert_used，否则「账号切换记录进任务结果元数据」无落地字段。

### M-6 Markdown 任务格式的回写机制缺失（P0 格式只有草案）
附录 A 的 Markdown 草案（L718-725）中：每条任务没有状态行（仅文件头一个 `<!-- status: pending -->`，语义不明——批级还是首任务级？），result 为空行。任务完成后**状态/结果写回 Markdown 的什么位置、原子替换后如何不破坏用户原有排版**（用户可能在任务区写代码块、多级列表），无任何定义。REQ-001 是一期 P0，此格式不能停留在草案。第 15 章待解决问题 7 只问了「如何区分指令与元数据」，没问回写。建议：补充回写规范；或一期采取「Markdown 只读输入 + 结果写入同目录独立结果文件」的简化策略并明示。

### M-7 重试策略叠加后无总尝试上限
临时限流重试 3 次（REQ-005）+ 普通失败重试 2 次（REQ-009）+ 每个新降级组合的重试（REQ-004）+ 兜底重试——单任务最坏尝试次数 = 组合数 × 重试数，且无总时长上限（叠加单任务 10 分钟超时后，一条任务可能运行数小时并拖住整批）。建议新增「单任务总尝试次数 / 总时长上限」配置，超限标记 failed 或 interrupted。

### M-8 账号池缺少预检
专家不可用有预检（故事 2.4，L286）、CLI 可用性有预检（REQ-010）、工作空间有预检（REQ-003a）——唯独账号池没有：过期/失效账号要轮到它执行时才暴露，中途才发现问题违背 REQ-010「快速失败」的理由。建议预检阶段对账号池做轻量可用性校验（一次极简调用），失效账号自动标记停用并提示。

### M-9 成功标准数字互相矛盾
执行摘要「≥ 50 条任务无人值守跑完」（L34）vs 发布计划 M3「每批 ≥ 20 条」（L560）——发布计划的验收门槛低于成功标准。另外「自动完成率 ≥ 95%（剔除任务本身错误）」中「剔除」无判定标准，建议改为可操作表述，如「失败任务 100% 有明确错误归因与日志」。

### M-10 REQ-020 自动关机的两个模糊点
① 「全部任务 done/failed 即正常完成」——存在 failed 也关机，与可选勾选「仅当失败率为 0 时关机」的默认关系未明示（当前写法默认允许带 failed 关机，建议显式说明默认行为）；② 未提 Windows/macOS 关机命令差异与权限要求，兼容性章节（L454-456）只圈了系统范围。

### M-11 受控并发（REQ-012）设计过于轻描淡写
并发场景下至少四个未解问题：多个 Agent 子进程共享「账号池 × 模型」额度状态（一个任务把额度跑耗尽会影响并发中的其他任务）、并发写任务文件与 REQ-006 原子回写冲突（需单写者或合并写策略）、并发时界面「当前任务/当前模型」的展示口径、终止时多子进程的回收顺序。P1 实现前需补充设计说明，否则这是一个陷阱需求。

### M-12 「切换成功率 100%」指标表述不严谨
L35「100% 切换成功并续跑」与风险表「额度错误误判」（L590）的现实矛盾——100% 意味着零漏判零误判，不可度量也不可承诺。建议拆分为：「降级机制触发率 100%（应触发必触发）」+「误切换率 ≤ X%（临时限流被误判为耗尽的比例）」。
