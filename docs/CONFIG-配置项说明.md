# 配置项说明（BatchAgentRunner v1.0）

> 面向「打开配置页/配置文件看不懂每一项」的场合。
> 全字段带注释模板见 [`samples/config.example.json`](../samples/config.example.json)。
> 字段口径的原始出处见 [PRD 第 9 章](PRD-BatchAgentRunner-v2.0.md)、[技术设计](DESIGN-BatchAgentRunner-v2.0.md)。

---

## 0. 配置文件在哪、怎么改

| 用途 | 路径 |
|------|------|
| 运行配置（桌面端读写的就是它） | `%LOCALAPPDATA%\BatchAgentRunner\config.json` |
| 额度冷却记录（重启后仍有效） | `%LOCALAPPDATA%\BatchAgentRunner\cooldowns.json` |
| 全字段带注释模板 | 仓库 `samples/config.example.json` |
| 运行日志 | 任务文件同目录 `runs/run-<时间戳>.log` |
| 汇总报告 | 任务文件同目录 `report-<时间戳>.json` / `.md` |

两种改法：

0. **配置向导（首次推荐）**：左侧导航「配置向导（首次推荐）」→ 按 6 步引导完成 执行工具 / CLI 检测 / 账号 / 模型 / 任务文件 / 保存。向导只写入账号、模型、执行工具、任务文件、全局默认工作空间这几项，其余高级项保持不变；保存后引擎自动重建。
1. **界面改**（推荐）：配置页分组填写 → 点「保存配置并重建引擎」。保存会重写整个 `config.json`，**注释会丢失**，所以别把注释当长期笔记。
2. **手改文件**：解析器允许 `//` 注释和尾随逗号，可以直接复制 `config.example.json` 过去改。改完重启程序生效。

> ⚠️ 改了账号 / 模型 / 时段 / 降级策略后必须让引擎重建（界面上的保存按钮会自动做），
> 否则调度用的还是旧矩阵。

## 1. 5 分钟跑通

### 1.1 不装 CLI 先验证工具本身

1. 配置页把 `agent_kind` 选 **Mock**（仿真适配器，不调任何 CLI）；
2. `task_file_path` 选 `samples/tasks.json`；
3. 到监控页点「预检」→ 应显示"预检通过：2 条任务，待处理 2 条"；
4. 点「开始」→ 观察状态流转：执行中 → 已完成，任务文件 `status` 被回写成 `done`。

Mock 用来验证调度逻辑（降级、时段跳过、冷却等待、兜底、危险操作拦截），不验证 Agent 的真实输出质量。

### 1.2 接真实 CLI

1. `agent_kind` 选 **WorkBuddy** / **CodeBuddy**；
2. 确认 PATH 里能直接跑 `workbuddy --version`（或 `codebuddy --version`）。跑不到就在 `cli_path` 写绝对路径；
3. 把各账号 `model_candidates[].name` 换成**该账号**真实可用的模型标识（默认的 `model-a`/`model-b` 是占位名；不同账号的池相互独立，按账号实际可用情况分别填）；
4. 把 `accounts[].credential_ref` 换成你的 CLI 登录 profile / 环境变量名；
5. 点「预检」——预检会逐个账号探测，探测失败的账号会被**自动停用**并给出警告。

## 2. 字段速查（按配置页的 9 个分组）

### ① 任务文件与执行工具

| 字段 | 默认 | 含义 / 什么时候改 |
|------|------|------|
| `task_file_path` | `""`（必填） | 任务清单。`.json` 原地原子回写状态与结果；`.md` 只读输入、状态写 sidecar `<name>.md.result.json`。运行日志与报告都写在它同目录。 |
| `agent_kind` | `WorkBuddy` | `WorkBuddy` / `CodeBuddy` / `Mock`。`Mock` 不调 CLI，用于自测与回归。 |
| `cli_path` | `null` | CLI 可执行文件路径。`null` = 在系统 PATH 里按默认名找（`workbuddy` / `codebuddy`）。装了多版本时写绝对路径最稳。 |
| `cli_arguments_template` | `null` | 参数模板。`null` = 用适配器内置模板。**2026-10-16 已实测校准**：内置 `WorkBuddy`/`CodeBuddy` 模板均为 `--output-format stream-json --include-partial-messages`（便于应用内实时输出流捕获逐行事件）。占位符：`{prompt}` `{model}` `{expert}` `{workspace}` `{extra}`。**切勿手写为 `--output-format text` 或纯 `--print`**——该模式下 CLI 全程不写 stdout，应用内实时流会空白（见 `CliCommandBuilder.cs` 注释）。 |

### ② 工作空间（决定 Agent 在哪个目录干活）

| 字段 | 默认 | 含义 |
|------|------|------|
| `workspaces[].name` | — | 命名空间名。任务里写 `workspace: "web"` 就解析到这条。 |
| `workspaces[].path` | — | 真实目录。预检时目录不存在会**直接报错拦住启动**。 |
| `workspaces[].is_global_default` | `false` | 勾中的那条作为全局默认空间。 |
| `default_workspace` | `null` | 本批默认空间（填命名空间名或绝对路径）。`null` = 走全局默认。 |

**生效优先级**：单任务 `workspace` 字段 › 本批 `default_workspace` › 全局默认 `is_global_default` › 程序当前目录。

> **数量上限（REQ-019，`max_workspaces`，默认 10）**：命名工作空间数量受此上限约束。已达上限时配置页「新增工作空间」按钮置灰且提交兜底拦截，提示「工作空间数量已达配置上限（当前上限 N 个）」（N 取配置值，非硬编码）。加载到的 `workspaces[]` 数量超过上限（如手工编辑 `config.json`）时，**预检（REQ-010）直接告警并拦截启动、定位到 `workspaces[]` 条目，不静默截断**。引擎不设绝对硬上限，以配置值为唯一校验准绳；配置页建议对输入范围作合理 UI 限制（如 1–100），但允许高级用户经 `config.json` 设更大值。

### ③ 账号池 × 候选模型（降级矩阵的两个维度；v1.12 起模型池挂在账号下）

| 字段 | 默认 | 含义 |
|------|------|------|
| `accounts[].id` | — | 账号标识，冷却记录按它落盘。**建议稳定不变**，改名会让历史冷却失效。 |
| `accounts[].display_name` | — | 界面/报告里显示的名字，随便起。 |
| `accounts[].credential_ref` | — | **凭据引用**，不是密码。**默认语义（凭证 Vault，DESIGN-账号凭证切换-v1.0）= Vault 内账号目录名，留空时取 `accounts[].id`**：配置页对该账号执行「引导登录」后，CLI 凭证快照按此名存入 `%LOCALAPPDATA%\BatchAgentRunner\vault\<cli>\<account_id>\`，切换 = 把快照原子回填为当前 Live 凭证（含保活回写）。保留显式覆盖语义：形如 `profile:xxx`、`env:XXX`、`keychain:xxx` 时按原方式生效——该值会以环境变量 `BATCH_AGENT_ACCOUNT=<credential_ref>` 注入子进程；其中 `env:XXX` 还会把环境变量 XXX 的值以 `CODEBUDDY_API_KEY` 注入子进程（2026-10-15 打通，codebuddy 2.167.0 实测读取该变量，这是 API Key 型多账号的生效方式）。明文一律不落盘、不写日志（Vault 内静态存储经 DPAPI 加密，审计只记账号 id 与哈希前 8 位）。注意：同一台机器的 CLI 登录态只有一个，多条 `profile:default` 实际是同一身份；文件型多账号请用「引导登录 + 快照」。 |
| `accounts[].enabled` | `true` | 停用的账号整个矩阵跳过。预检不通过会被自动置 `false`。 |
| `accounts[].model_candidates[]` | `null` | **该账号自己的有序候选模型池**（v1.12 新增）。矩阵 = 各账号 × 自有池，账号之间互不共享。未配置（null/缺省）时该账号回退到全局 `model_candidates`。 |
| `accounts[].model_candidates[].name` | — | 模型标识，原样传给 CLI 的 `--model`。账号内唯一；**不同账号可配同名模型**（如 A、B 账号都有 Hy4），但时段/单价/冷却各自独立。顺序 = 该账号内降级优先级。 |
| `accounts[].model_candidates[].free_time_window` | `null` | 免费时段，**按「账号 × 模型」组合生效**：同一模型在 A 账号可设 0:00–8:00、在 B 账号设 0:00–24:00。`null` = 全天可用。见下方「时段语义」。 |
| `accounts[].model_candidates[].estimated_unit_price` | `null` | 预估单价（元/次），CLI 不返回费用时用于估算。 |
| `accounts[].fallback_models[]` | `[]` | **该账号自己的有序兜底模型池**（v1.12 新增）：兜底触发时按「账号顺序 × 账号内兜底池顺序」取第一个可用兜底组合；兜底模型不参与免费时段过滤。总开关与成本上限是全局的，见 ⑤。 |
| `model_candidates[]`（顶层全局） | `[]` | **向后兼容字段**：全局共享候选列表，仅对未配置自有池的账号生效；账号配置了自有池时全局列表对该账号不生效。 |
| `degradation_strategy` | `ModelFirst` | `ModelFirst`：同一账号先轮完**该账号自己的**候选模型池，池全耗尽再换账号。`AccountFirst`：按模型名聚合——先把同一模型名在所有配置了它的账号上轮完，再换下一个模型名（模型名按各账号候选池中的首次出现顺序）。 |

**时段语义（容易理解错，重点看）**

- 时段的配置粒度是「账号下的模型项」，判定针对「账号 × 模型」组合：`A 账号 Hy4 0:00–8:00` 与 `B 账号 Hy4 0:00–24:00` 是两个独立组合，A 账号 8 点后跳过 Hy4 时 B 账号的 Hy4 照常可用。
- 不在免费时段内 → 该组合被**时段外跳过**：不计任务失败、不触发切换告警、不污染误切换率统计，纯属预期调度行为。
- `start` > `end` 视为跨零点，如 `22:00 → 06:00`。
- `days` 的语义是**时段覆盖日**：跨零点时段会同时看开始日与结束日——`周日 22:00 → 周一 06:00` 因为覆盖到周一，所以在配置了周一的情况下也算命中。
- 判定以**本机挂钟时间**为准。改系统时间 / 休眠唤醒会让时段判定漂移，系统恢复后会立即重评。

|------|------|------|
| `expert.kind` | `None` | `None` = 走 CLI 默认智能体；`Single` = 单专家；`Team` = 专家团。 |
| `expert.id` | `null` | 专家/专家团 ID，填进参数模板的 `{expert}`。 |

### ⑤ 特殊模型兜底（默认关闭；v1.12 起兜底模型池挂在账号下）

| 字段 | 默认 | 含义 |
|------|------|------|
| `fallback.enabled` | `false` | 总开关（**全局**，约束所有账号的兜底行为）。 |
| `fallback.model` | `""` | **已废弃（v1.12）**：兜底模型改为按账号配置（`accounts[].fallback_models`），此字段不再被引擎消费，仅为旧配置兼容保留解析。 |
| `fallback.max_cost_per_task` | `1.0` | 单任务兜底花费上限（元，全局）。估算单价超过它就不兜底这个任务。 |
| `fallback.max_cost_per_batch` | `10.0` | 整批兜底总上限（元，全局）。累计超了 → 停用兜底并转阻塞。 |
| `fallback.estimated_unit_price` | `null` | **已废弃（v1.12）**：单价随账号下的兜底模型项配置（`accounts[].fallback_models[].estimated_unit_price`）。 |

**兜底模型池怎么配（v1.12）**：在需要兜底能力的账号下加 `fallback_models`（有序数组，项 = `name` + 可选 `estimated_unit_price`）。触发时按「账号顺序 × 该账号兜底池顺序」取第一个可用兜底组合；兜底执行本身失败按普通失败处理，不循环兜底（边缘情况 10）。至少一个启用账号配置了兜底模型才具备兜底能力（预检会告警）。

**触发条件（两个都要满足）**：① 当前任务**已经开跑过**（至少有一次尝试或已有部分输出）；② 免费组合矩阵当前全部不可用。
免费组合一个都没用过时不触发兜底，直接走等待或阻塞。

### ⑥ 重试 / 超时 / 上限

这四个是**不同层级的闸门**，从窄到宽：

```
单次执行超时 ──→ 单任务总时长上限 ──→ 单任务总尝试次数上限 ──→ 单批最长可等待
 task_timeout      max_total_minutes      max_attempts            max_wait
```

| 字段 | 默认 | 含义 |
|------|------|------|
| `max_retries_per_task` | `2` | 普通失败（非限流/非额度/非危险操作）的重试次数。`0` = 不重试直接判失败。 |
| `rate_limit_backoff_retries` | `3` | 临时限流（429 之类）的退避重试次数。**退避期间重试的是同一账号+同一模型**，用完仍失败才升级为"额度耗尽"去切组合。 |
| `rate_limit_initial_backoff_seconds` | `5` | 退避起始秒数，指数增长 `5 → 10 → 20 → 40…`，单次上限 2 分钟。 |
| `task_timeout_minutes` | `10` | 单次执行超时。超了判该次失败，**已产生的部分输出会保留**。 |
| `max_attempts_per_task` | `10` | 单任务总尝试次数上限（切模型、切账号、退避重试都算一次）。防止无限重试。 |
| `max_total_minutes_per_task` | `60` | 单任务总时长上限，从任务开始计时，含所有重试与切换。 |
| `max_wait_minutes` | `60` | **仅对「免费时段外」类等待**生效：所有组合因时段外不可用时，最早恢复时间在此之内 → 进「等待恢复」；超出 → 直接转「已阻塞」。额度耗尽（`QuotaReset`）的等待不受此限（见下）。 |
| `wait_for_quota_reset` | `true` | 所有账号的所有候选模型**都因额度耗尽**而同时不可用时，进入「等待恢复」并无限等待最早恢复的组合额度重置后自动续跑（额度每日必然重置，确定可恢复）；暂停期间不计入批处理与各任务的时长。关闭后额度耗尽等待同样受 `max_wait_minutes` 约束。若不可用还夹杂账号停用 / 免费时段外，则不算"纯额度耗尽"，仍按 `max_wait_minutes` 判定。 |
| `default_cooldown_minutes` | `60` | CLI 报错里**解析不到**额度重置时间时的降级冷却时长。 |

### ⑦ 并发 / 续跑 / 失败即停

| 字段 | 默认 | 含义 |
|------|------|------|
| `concurrency` | `1` | 同时执行的任务数。`1` = 严格串行（推荐）。`>1` 会并发拉起多个 CLI 子进程，但账号/额度是共享的，更容易撞限流。 |
| `force_rerun` | `false` | `true` = 忽略已完成状态全部重跑；`false` = 已 `done`/`failed` 的跳过（这就是「续跑」的语义）。 |
| `stop_on_failure` | `false` | `true` = 某条任务重试用尽仍失败时，整批立刻转「已阻塞」。 |
| `terminate_after_current_task` | `false` | 预留开关。界面上「终止」和「跑完当前再停」是两个独立按钮，**当前版本引擎未读此项**。 |

### ⑧ 自动关机（默认关闭）

| 字段 | 默认 | 含义 |
|------|------|------|
| `auto_shutdown.enabled` | `false` | 总开关。 |
| `auto_shutdown.only_when_zero_failure` | `false` | `true` = 只有失败数为 0 才关机；`false` = 允许带着 failed 关机。 |
| `auto_shutdown.countdown_seconds` | `60` | 可撤销倒计时（秒）。批处理完成后弹出倒计时窗口，倒计时走完才真正调用系统关机；窗口内点「取消关机」即中止。设为 `0` 则跳过窗口直接执行（不推荐）。 |

关机只在**批级状态为"已完成"且结果 100% 落盘、报告写完之后**才触发，不会丢结果。权限不足时降级为"提示手动关机"并记录原因。

> **倒计时在哪里走**：在**应用内**计时（`Core/Engine/AutoShutdownCoordinator` + 倒计时窗口），不在操作系统层排程。
> 因此本工具进程不在（崩溃/被结束）时**不会关机**——这是有意的失效保护；系统关机命令本身仍是立即执行（`shutdown /s /t 0`）。
> 无论倒计时如何结束，报告的 `shutdown` 段都会记录 `executed` 与原因（含"用户已取消"）。

### ⑨ 交互自动应答与危险操作防护

这是无人值守的核心安全阀。机制：

```
CLI 静默超过 stdin_idle_seconds
   └─▶ 判定为「在等确认」
         ├─ 命中 dangerous_blacklist → 拒绝自动批准，杀进程，该任务判失败
         ├─ 命中 allowed_whitelist   → 视为允许，注入 default_answer / 选择默认选项，记日志
         └─ 都没命中                → 注入 default_answer / 选择默认选项，记日志
```

| 字段 | 默认 | 含义 |
|------|------|------|
| `auto_answer.dangerous_blacklist` | 18 条 | 命中即**绝不**自动批准。默认覆盖 `rm -rf`、`git push --force`、`删除文件` 等。 |
| `auto_answer.allowed_whitelist` | 6 条 | 命中即视为允许。**白名单优先级高于黑名单**，所以别把危险词写进白名单。 |
| `auto_answer.default_answer` | `"y"` | 普通确认型交互注入 stdin 的默认应答内容。多数 CLI 的确认默认项就是 `y`。 |
| `auto_answer.stdin_idle_seconds` | `30` | 静默多少秒判定为"在等输入"。设太小会误判——模型思考时间长时也会静默。 |
| `auto_answer.choice_prompt_patterns` | 7 条 | 识别**选择型**交互的关键词。提示文本含任一关键词且能提取编号选项时，按 `default_choice_index` 选择对应选项。 |
| `auto_answer.choice_option_pattern` | 见默认正则 | 匹配选项行的正则。第 1 捕获组为选项编号/键，第 2 组为选项文本。默认覆盖 `1. xxx`、`1、xxx`、`1) xxx`、`[1] xxx` 等。 |
| `auto_answer.default_choice_index` | `0` | 选择型交互默认选择的选项索引（0-based）。`0` 表示第一个选项。 |

判定基于**提示文本的关键词包含匹配**，所以黑名单词条必须覆盖你所用 CLI 的实际措辞。误判了就在这里补词。

> 选择型示例：CLI 输出 `请选择：\n1. 方案 A\n2. 方案 B\n>` 时，会自动注入 `1`（第一个选项）。若你想要的不是第一个，调整 `default_choice_index` 或把该场景写进白名单/黑名单。

### ⑩ 其它

| 字段 | 默认 | 含义 |
|------|------|------|
| `result_max_kb` | `100` | 单任务结果写入任务文件的大小上限（KB）。超出截断并提示完整内容见运行日志。 |
| `backup_retention` | `5` | 任务文件自动备份保留份数。每次启动前备份一次，更旧的自动删；`0` = 不备份。 |
| `credits_claim.enabled` | `true` | 每日积分领取总开关：关闭后领取入口不可用。 |
| `credits_claim.auto_before_batch` | `false` | 每次批量任务开始前自动为所有启用账号领取（失败不阻断批处理）。 |
| `credits_claim.force` | `true` | 强制领取（允许重复领取）：忽略台账去重，每次都去调领取接口；服务端若判定今日已领过会回「今日已领取过」，但不会在本地跳过。`false` = 恢复「同账号每日一次」去重，今日已领过的账号自动跳过。 |

## 3. 关键机制（配之前最好先懂这几条）

### 3.1 组合可用性 = 时段约束 ∩ 额度约束

一个「账号 × 模型」组合可用，当且仅当**同时**满足：

- 不在免费时段外（时间维度；时段取该账号下模型项自己的配置——同名模型在不同账号可配不同时段）
- 不在额度冷却中（额度维度）

恢复时间 = `max(下一免费时段开始, 额度重置时间)`。两个约束互相独立，取更晚的那个。

### 3.2 Waiting vs Blocked

| 状态 | 含义 | 怎么走出来 |
|------|------|------|
| `waiting`（等待恢复） | 所有组合暂不可用。**纯额度耗尽**（`wait_for_quota_reset` 开启时）会无限等待额度重置；**免费时段外**则在 `max_wait_minutes` 之内等待 | 自动：等到点或额度重置后继续；中途补充额度/改配置也会提前唤醒；也可手动取消。**暂停时间不计入批处理与任务时长** |
| `blocked`（已阻塞） | 免费时段外且恢复时间超出 `max_wait_minutes`、或关闭了 `wait_for_quota_reset` 且额度耗尽超出 `max_wait_minutes`、或兜底超限、或失败即停 | 手动：补额度 / 加账号模型 / 调时段 → 点「续跑」 |

取消等待 = 转 `blocked`，并提示下一可用恢复时间点。已 `done` 的任务不受影响。

> 时长口径：`总耗时` 为墙钟总时长（含暂停等待），`净执行` 为 `总耗时 − 时段外等待 − 额度冷却等待`，即暂停等待不计入。报告页与单任务行均展示净执行时长。

### 3.3 时段外跳过 / 冷却跳过 ≠ 失败

两者都是**预期调度行为**：不计任务失败、不触发切换告警、不影响误切换率统计。只有真正执行了并失败才算失败。

### 3.4 切换与"继续当前任务"

额度耗尽 → 切下一个组合，**以该任务的完整指令重新发起一次全新会话**，不继承上一次上下文。
已产生的磁盘副作用保留，最终结果由指令自身的幂等性决定（PRD 第 10 章技术决策 2）。

### 3.5 额度耗尽怎么判定

靠 CLI 报错文本的关键词模式匹配（`QuotaErrorClassifier`）。额度关键词优先于限流关键词。
**误判率是本项目已知的主要风险**——模式库要靠 M0 V-3 摸底各 CLI 的实际错误特征来扩充。
冷却记录会落盘，工具重启后依然有效。

## 4. 常见坑

| 现象 | 原因 / 处理 |
|------|------|
| 点「开始」没反应 | `task_file_path` 没选。「开始」按钮在该字段为空时是禁用的。 |
| 预检报「工作空间目录不存在」 | `workspaces[].path` 指向的目录不存在。预检会拦住启动，这是设计如此。 |
| 所有任务都被跳过，提示时段外 | 某「账号 × 模型」组合配了 `free_time_window` 但当前不在窗口内。注意时段是组合级的：A 账号 8 点后跳过 Hy4，不代表 B 账号的 Hy4（若配了全天）也不可用。把时段放宽，或删掉该项变成全天可用。 |
| 某账号的模型池没生效 | 该账号配置了自己的 `model_candidates` 时，全局 `model_candidates` 对它不生效（自有池优先）；两边都没配的账号才会告警无可用模型。 |
| 明明额度还有却提示冷却中 | 上次跑批记下的 `cooldowns.json` 还在。监控页有「重置冷却」按钮可清空。 |
| 任务卡住不动，一直 waiting | 恢复时间还没到。想立刻跑：改时段/补账号模型（会自动唤醒），或点「取消等待」转 blocked 后手动续跑。 |
| 危险操作被拦、任务判失败 | 命中了黑名单。这是**有意的安全阀**，不是 bug。如果确认某条提示是安全的，加进白名单。 |
| CLI 没反应直到 30 秒后才继续 | `stdin_idle_seconds` 的正常表现——它在等确认。确认文案若不匹配黑/白名单，会注入默认应答。嫌慢可调小，但要小心误判。 |
| 兜底没触发 | 免费组合一个都没用过时不触发兜底（只在"已投入执行"的任务上兜底）。 |
| 配置里的注释不见了 | 在界面点过「保存配置」就会重写文件、丢注释。以 `samples/config.example.json` 为准。 |
| 改了配置不生效 | 账号/模型/时段/降级策略改了要重建引擎。界面保存按钮会自动重建；手改文件要重启程序。 |

## 5. 待真实任务校准的默认值

| 字段 | 当前默认 | 校准依据 |
|------|---------|---------|

| `max_wait_minutes` | 60 | 你的免费时段/额度重置周期有多长（等不到就该转 blocked 去睡觉） |
