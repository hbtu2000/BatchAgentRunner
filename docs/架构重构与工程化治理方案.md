## 1. 现状诊断

### 1.1 架构问题
- **A1 依赖倒置**：`Desktop` 直接引用 `Infrastructure`/`Agents` 的**具体类型**并手工 `new`，UI 层成为组合根（P1-4/P1-5）。分层规则"Core←Infrastructure←Desktop"被打破。**✅ 已收口（2026-10-19）**：`IEngineFactory`/`IEngineHost` 引入后，组合根下沉 `Desktop/Composition/EngineFactory`，三处残留装配（`CredentialVaultHost.CreateDefault`、`EngineHost` 的 `ShutdownService`、`TemplateEditorViewModel` 的 `FileWorkflowTemplateStore`）全部收回；§4.3「Desktop 不得直接 new Infrastructure 具体类型」IL 扫描断言落地，结构上防复发。
- **A2 Core 越层**：`Core/Scheduling/GateEvaluator.cs` 在领域层直接 `new Process()` + `cmd.exe /c`，进程能力泄漏进领域层（P1-9）；`BatchEngine.cs` 多处绕过自有 `ITaskFileStore` 直接文件 IO（P1-10）。
- **A3 God Object**：`BatchEngine` 单文件 1960 行、16 类职责、60+ 公开成员、14 参数构造，是最大变更放大器（P1-1/P1-2/P1-3）。
- **A4 全局可变状态**：`CredentialLocationRegistry` 为 `public static class` + 非线程安全 `Dictionary` + `SetLiveRootOverride` 全局路径注入，被 UI 生命周期意外改写（P1-16，原 P1-8）。

### 1.2 代码坏味道
- **B1 超长方法/状态机**：`ExecuteTaskAsync` 249 行、`PreflightAsync` 196 行，含 `while(true)+switch+goto case`（P1-2，圈复杂度 >35）。
- **B2 重复实现**：`Truncate` 三份、终态集合三份、失败分派状态机逐字重复、`Clone` 六份手写、`Json*Store` 三份逐行同构、`"BatchAgentRunner"` 路径魔法串 9 处硬编码（P2-1~P2-6、P2-31）。
- **B3 吞异常**：src 内 `catch (Exception)` 占比 53%（基线 42/79），空 `catch { }`/仅记 WARN 是排障困难主因（§4.3 复杂度/评审墙目标）。
- **B4 同步阻塞**：`GetAwaiter().GetResult()` / `.Result` 在 `MainViewModel.cs:20`、`EngineHost.cs:136`（P1-6）。
- **B5 内存泄漏隐患**：事件 lambda 订阅全程无 `-=`，行 VM 被长生命周期 `TaskItem` 永久持有（P1-7）。
- **B6 误导注释**：147 处中文注释（"二期扩展""暂不支持"）与实现脱节，计划性延期未进台账，比无注释更危险（P2-26）。

### 1.3 依赖与工程短板
- **D1 包版本散落**（已修）：引入 CPM 前版本手写、存在无效依赖（如 `Logging.Abstractions` 引用 0 处使用），已上 `Directory.Packages.props` 结构性防漂移（P1-17✅）。
- **D2 无 CI 门禁**（已建但弱）：`.github/workflows/ci.yml` 仅 build+test **只报告不阻断**；分支保护/必需状态检查**仍未在 GitHub 配置**，红 CI 不阻止合并（台账 §5.3 边界 2）。
- **D3 测试分层不足**：E2E/Usability/Process 已打 `Trait`，Desktop 已从 13 项冒烟增至 39 用例（含架构断言 3 项 + VM 白箱，2026-10-19 实跑），高危模块仍 4 项零覆盖（P1-15 余 `CodeBuddyCreditsApiClient`/`BackupManager`/`LocalGitIntegration`/`ShutdownService`）。
- **D4 钩子非 clone 继承**：`commit-msg`/`pre-commit` 钩靠本机 `core.hooksPath`，clone 不自动生效，新人/CI runner 需手动启用（台账 §5.3 边界 1/5）。
- **D5 历史未净化**：`git rm --cached` 仅移出索引，已入库的隐私产物（`.tmp_reflect.ps1` 含个人绝对路径、`TaskList/tasks.xlsx` 真实运行数据）仍在历史中，彻底净化需 `git filter-repo`（高风险，机会主义项）。

### 1.4 风险点（最高优先级）
- **R1 拆 `BatchEngine` 丢语义**：其承载"降级矩阵/冷却/兜底计费/时段窗口"等**未被设计文档完整覆盖的业务规则**，重写必然丢语义——只能 strangler fig（台账 §3.3 已明令禁止重写）。
- **R2 动骨期回归**：阶段 2 是首次对运行核心做结构改动，一旦破坏调度正确性（误降级、漏判配额重置、并发写损坏）即用户侧数据丢失。
- **R3 架构断言未固化**：分层规则曾只在文档、无测试兜底，重构期易回潮。**✅ 部分落地（2026-10-19）**：§4.3 八条断言中 5 条已以反射测试固化（Core 引用方向、Core 禁 `Process`、Desktop 禁 `new` Infrastructure、Desktop 禁直引 `BatchEngine` 等，`LayeringRulesTests` ×2 项目）；余 3 条（Avalonia 越层、`INotifyPropertyChanged` 进 Domain、生产禁 `FakeClock`/`Mock*`）与 ArchUnitNET 批次留在迭代 2/3。

## 2. 重构目标与边界

### 2.1 目标
在不改变对外行为契约（CLI 调用语义、配置 schema、任务文件格式、报告格式、UI 用户操作流程）的前提下：
1. 拆掉 `BatchEngine` 这个唯一变更放大器，使其可独立测试、职责清晰；
2. 拉直依赖方向，UI 不再倒置、Core 不再越层；
3. 建立"防新增"的工程化闭环（提交门禁 + 编译门禁 + 架构断言 + 复杂度门禁 + PR 清单 + 债务预算）；
4. Desktop 由"结构上不可测"转为可测、关键契约有测试锁住。

### 2.2 明确不动（冻结清单）
- **契约层全部不动**：`RunOptions`（40+ 配置项是产品契约）、任务文件 JSON/Markdown 格式、报告 JSON/MD 格式、CLI 命令行参数契约、凭据文件格式与迁移路径（`FileCredentialVault`）。
- **领域知识密集组件禁止重写**：`BatchEngine`（只能 strangler fig）、`WorkflowTypes`/`DagScheduler` 的调度语义、`BatchReport` 聚合口径。
- **用户已确认的技术选型不动**：C#/.NET 10、Avalonia 12 桌面 UI、Core/Agents/Infrastructure/Desktop/Tests 五层、`MockAdapter` 仿真通道。

### 2.3 改造范围（阶段 2/3）
- 提 `IBatchEngine` 接口（P1-3）✅ 阶段 2 已完成（2026-10-19）；引入 DI + `IEngineFactory`（P1-4/P1-5）✅ 阶段 2 已完成并收口（2026-10-19：组合根为唯一 `new` 点 + §4.3 IL 断言）；
- `BatchEngine` 按 6 协作者拆分（P1-1）✅ 阶段 2 已完成 + 状态机外置（P1-2）✅ 阶段 2 已完成；
- `IProcessRunner` 抽离把进程 IO 赶出 Core（P1-9）✅ 阶段 2 已完成；引擎内 IO 全走 `IFileSystem`/`ITaskFileStore`（P1-10）✅ 阶段 2 已完成；
- 取消 `CredentialLocationRegistry` 静态入口（P1-16）✅ 阶段 2 已完成；`IClock`/`IProcessLauncher` 注入缝补全（P2-21 已部分）；
- Desktop 补测试 + 契约收敛（P1-19）⏳ 阶段 2 唯一剩余项；同步阻塞改异步（P1-6）；事件订阅 `-=`（P1-7）；
- 剩余高危盲区补测试（P1-15 余 4 项）；重复实现收敛（P2-1~P2-6、P2-31）；误导注释清算（P2-26）。

### 2.4 禁止范围（架构师红线）
- ❌ 一次性全量重写 `BatchEngine` 或 Desktop——禁止，只能 strangler fig + 补测试。
- ❌ 改变任何对外契约（配置字段名、任务文件 schema、CLI 参数、报告格式）——除非用户显式批准并走迁移。
- ❌ 引入新的第三方 DI 框架/重型基础设施——以最小 DI（构造函数注入 + 工厂）收口，不引入 MediatR/Autofac 等。
- ❌ 在动骨期（阶段 2）并行开发新功能——冻结新功能，按台账 §4.6 动骨期 50% 容量还债。

### 2.5 兼容策略
- **接口兼容**：`BatchEngine` 外壳保留为 `IBatchEngine` 的门面实现，过渡期内旧调用点不改；新代码一律只依赖 `IBatchEngine`（架构断言强制）。
- **配置兼容**：配置 schema 只增不破；新增派生/计算属性必须 `[JsonIgnore]`，集合类型不声明为接口（既有的解析器约束）。
- **行为等价锁**：每次拆出的协作者，先用既有黑箱测试 + 新增不变量测试锁定行为，再替换；CI 全量测试 0 失败为合并硬门槛。
- **分步可回滚**：每步单 PR、单提交、`git diff --stat` > 400 行即回退重切。

## 3. 架构优化方案

### 3.1 分层与依赖方向（强制单向）
```
Desktop  ──▶ Core (领域 + 引擎抽象 + 端口接口)
   │            ▲
   │ 经 IEngineFactory / 端口接口
   ▼            │
Infrastructure ── 实现 Core 定义的端口（IProcessRunner / ITaskFileStore / IVault / INotifier）
   ▲
Agents ── 实现 Core 定义的 IAgentAdapter（含 MockAdapter）
```
- **规则**：`Core` 只定义领域与端口接口，**绝不**引用 Infrastructure/Agents/Desktop；`Core`/`Infrastructure` 不得出现 `Avalonia.*`；`Desktop` 不得 `new` Infrastructure 具体类型（只经 `IEngineFactory` 与端口接口获取）。
- **落地手段**：已用反射测试固化 5 条关键规则（`LayeringRulesTests`，含 IL 扫描「Desktop 不得直接 new Infrastructure 具体类型」，2026-10-19）；ArchUnitNET 作为后续增强批次（§4.9 迭代 2/3），替代/扩容现有反射断言。

### 3.2 端口（Port）定义（Core 出，Infrastructure/Agents 入）
| 端口接口 | 归属层 | 承接能力 | 解决 |
| -- | -- | -- | -- |
| `IBatchEngine` | Core | 引擎对外门面 | P1-3 |
| `IEngineFactory` | Core | 组装引擎 + 协作者 | P1-4/5 |
| `IProcessRunner` | Core(定义)/Infra(实现) | 进程启动/读取/杀树（原生 `Kill(entireProcessTree:true)`） | P1-9、P1-13 |
| `ITaskFileStore` | Core(定义)/Infra(实现) | 任务文件读写（JSON 原地原子写、MD sidecar 回写） | P1-10 |
| `ICredentialVault` | Core(定义)/Infra(实现) | 凭证存取（引用而非明文） | P1-11/16 |
| `IClock` / `IProcessLauncher` | Core(定义) | 可测时间/启动缝 | P2-21 |
| `INotifier` / `IReportBuilder` | Core(定义)/Infra(实现) | 通知/报告聚合 | P1-1 协作者 |

### 3.3 模块解耦：`BatchEngine` strangler fig 拆法
保留外壳 → 职责逐个外迁 → 外壳转门面 → 最后删除。每步可编译、可测试、可回滚。

| 步 | 拆出协作者 | 承接原职责 |
| - | -- | -- |
| 1 | `ITaskDispatcher` | 派发/并发控制、DAG 判定 |
| 2 | `ITaskRunner` | 单任务状态机（重试/退避/降级/超时） |
| 3 | `IFallbackBilling` | 兜底模型选择与计费（承载 P0-1/P0-5 成本不变量） |
| 4 | `IGitWorkflow` | Git 建分支/开 PR、diff 采集、Markdown 回写 |
| 5 | `INotifier` + `IReportBuilder` | 通知、报告/用量/时间线聚合 |
| 6 | `IPreflight` | 启动预检 |

> 过渡期约束：**新代码一律不得引用 `BatchEngine` 内部成员**，只允许走 `IBatchEngine`（架构断言强制，§4.3）。

### 3.4 边界定义
- **进程边界**：一切进程能力经 `IProcessRunner`，Core 内禁止 `System.Diagnostics.Process`。
- **IO 边界**：一切文件 IO 经 `ITaskFileStore`/`AtomicFileWriter`；原子写是硬约束（P0-8）。
- **UI 契约边界**：`TaskItem` 等领域对象不得实现 `INotifyPropertyChanged`（P2-7）；UI 绑定走 `TaskItemViewModel` 防腐层。
- **色彩/常量边界**：XAML 不得写字面色值，统一走设计 token；路径/魔法串收口常量（P2-31）。

## 4. 代码重构策略

### 4.1 命名
- 端口接口统一 `I` 前缀 + 能力名词（`IProcessRunner` 而非 `ProcessHelper`）；协作者以职责命名（`FallbackBilling` 而非 `BillingUtil`）。
- 消除中文方法名进生产契约的歧义：生产代码标识符保持 ASCII；仅注释与 UI 文本用中文。

### 4.2 职责拆分
- 严格按 §3.3 六步把 `BatchEngine` 16 类职责归位；每拆一个协作者，同步删除 `BatchEngine` 内对应的私有方法，避免"拆了还留着"。
- 状态机外置：把 `ExecuteTaskAsync` 的 `while+switch+goto` 改为显式状态枚举 + 转移表/状态对象，圈复杂度从 >35 压到 ≤15。

### 4.3 消除重复
- `Truncate`/`Clone`/终态集合/失败分派：抽公共工具或改 `record with`（P2-6），删除手写副本。
- `Json*Store` 三份同构：抽 `JsonStoreBase<T>` 泛型基类（构造 + 默认目录 + `LoadAsync` catch + 原子保存），路径常量收口一处（P2-31）。

### 4.4 简化逻辑
- 同步阻塞改异步：`MainViewModel`/`EngineHost` 的 `GetAwaiter().GetResult()` 改为异步初始化门（P1-6）。
- 全局静态状态消除：`CredentialLocationRegistry` 改为显式传入，取消 `static Dictionary` 与 `SetLiveRootOverride`（P1-16）。

### 4.5 异常处理
- 禁止空 `catch { }`；允许 `catch` 后**保留原异常对象**并记日志，但必须区分"可容忍降级"与"应中止"。
- 降级/兜底/额度冷却跳过属**预期调度行为**：不计失败、不触发切换告警、不污染误切换率（已有领域语义，重构中保持）。
- 目标：CI 跟踪 `catch (Exception)` 占比，从 53% 逐季度下降；新增空 catch 一律 PR 清单拒绝（§4.5）。

### 4.6 事件与生命周期
- 引擎→UI 事件经 `EngineHost` 单一 `UiThread.Post` 收敛（P0-6/7 已落地），后台线程 `await` 后不得直接改 UI 集合。
- 长生命周期对象（如 `TaskItem`）对短生命周期 VM 的订阅必须 `-=` 或在 `Dispose` 中退订（P1-7）。

## 5. 工程化治理方案

### 5.1 目录与工程规范（已落地 + 待补）
- ✅ `Directory.Build.props`：`TreatWarningsAsErrors=true` + `EnforceCodeStyleInBuild` + `AnalysisLevel=latest-recommended`。
- ✅ CPM：`Directory.Packages.props` 集中版本（NU1008 防漂移）。
- ⏳ 提供 `tools/setup-hooks.sh` 一键启用本机钩子（解决 D4 clone 不继承）。
- ⏳ 仓库历史净化脚本（D5，`git filter-repo`，高风险单独评审）。

### 5.2 编码规范
- `.editorconfig` 40+ 条规则已在构建期执行（P0-15✅）；UTF-8 源码（`CodePage=65001`）+ `end_of_line=lf` + `.gitattributes eol=lf`（P0-12 格式门禁✅）。
- `pre-commit` 钩 `dotnet format --verify-no-changes`（CHARSET 假阳性按台账 §4.7 #9 过滤）。

### 5.3 单元测试与测试分层
- 分层：`[Trait("Category", …)]` = 单元 / E2E / Usability / Process；CI 快跑单元、慢跑 E2E·Usability·Process。
- 不变量测试：为"一眼看不出是错的"缺陷补断言式测试（如 P0-1 成本截断、P0-4 并发写串行）。
- 盲区补齐：阶段 2 顺带补 `CodeBuddyCreditsApiClient`/`BackupManager`/`LocalGitIntegration`/`ShutdownService` 4 项（P1-15 余）。
- Desktop 测试：Avalonia headless 测试基座，覆盖线程收敛与关键契约（P1-19）。

### 5.4 CI/CD
- ✅ 现有 CI：`windows-latest` + `dotnet build --no-incremental` + 分层 test，**必须 `--no-incremental`**（否则复现 P0-12 的 0 警告假象）。
- ⏳ **阻断化**：在 GitHub 配置分支保护/必需状态检查，使红 CI 真正阻止合并（当前最大残留短板）。
- ⏳ 覆盖率门槛：阶段 1 已接 coverlet，下一步设"高危模块覆盖率 ≥ X%"软门槛，再转硬门槛。
- 门禁顺序：先 warning 不阻断 → 再转 error；复杂度阈值先按基线标定（单文件 ≤800、单方法 ≤60、圈复杂度 ≤15、构造参数 ≤7），逐季度收紧（§4.4）。

### 5.5 静态扫描与架构断言
- **编译期**：分析器 + `TreatWarningsAsErrors`（新增警告即构建失败）。
- **架构期**：分层规则已用反射测试固化 5 条（2026-10-19，`LayeringRulesTests`；含「Desktop 不得直接 new Infrastructure 具体类型」IL 扫描断言）；ArchUnitNET 批次（迭代 2 排期）负责扩容余下规则与统一表达。
- **复杂度期（迭代 3 排期）**：上述阈值先 warning，后 error。
- **逃逸阀**：任何豁免 `#pragma`/`[SuppressMessage]`/`NoWarn` 必须附理由 + 到期日 + 责任人，登记台账 §4.7；到期未清自动升 P1。

### 5.6 日志 / 配置 / 文档
- 日志：结构化日志（现 `ILogger` 引用 0 处——P1-17 删了无效依赖，但生产代码也基本没接日志；阶段 2 在协作者里接 `ILogger`，关键路径留痕但不吞异常）。
- 配置：生产 API 地址/路径从默认值抽为配置或常量（P1-21），避免测试打到生产；配置 schema 只增不破。
- 文档：误导注释清算（P2-26）；每次拆协作者同步更新 DESIGN 文档；计划性延期必须进台账而非写注释。

### 5.7 PR 评审清单（合不进）
强制勾选：①是否让某文件行数/复杂度上升（说明理由）；②是否新增空 catch / 仅记 WARN；③是否新增可变 static 状态；④是否新增 `.GetResult()`/`.Result`/`.Wait()`；⑤后台线程 await 后是否直接改 UI 集合；⑥是否新增文件 IO 未走原子写；⑦是否拼接命令行而非 `ArgumentList`；⑧是否新增硬编码色值/魔法数字/绝对路径；⑨高危路径是否带测试；⑩提交信息是否含"改了什么/为什么"。

## 7. 风险清单 + 回滚方案 + 验收标准

### 7.1 风险清单
| 风险 | 触发 | 影响 | 缓解 |
| -- | -- | -- | -- |
| 拆 `BatchEngine` 丢调度语义 | 协作者行为不等价 | 误降级/漏判配额/数据损坏 | strangler fig + 不变量测试锁行为；每次只拆一个协作者 |
| 并发回归 | 单写者/锁改动 | 状态回退/文件损坏 | 保留 P0-4/P0-5 不变量测试；并发专项测试 |
| 架构回潮 | 新代码直引内部 | 倒置复发 | ArchUnitNET 断言 + PR 清单 |
| CI 不阻断 | 分支保护未配 | 红 CI 仍合并 | 推动仓库管理员配必需状态检查（最高优先级待办） |
| 钩子未生效 | clone 不继承 | 脏提交入库 | `tools/setup-hooks.sh` + CI 兜底（`TreatWarningsAsErrors`） |
| 历史隐私残留 | filter-repo 误操作 | 历史破坏 | 单独评审、备份后执行、不在动骨期做 |

### 7.2 回滚方案
- **单步回滚**：每阶段单 PR、单提交；`git diff --stat` > 400 行即回退重切。合并前随时 `git revert` 该提交。
- **行为回退**：任一协作者拆分后全量测试失败 / 不变量测试红 → 该协作者回退为 `BatchEngine` 内联实现（门面外壳保留，调用点不变），不影响其他协作者。
- **发布回退**：`BatchEngine` 外壳与 `IBatchEngine` 门面长期保留，即使内部全拆完，对外调用契约不变，可整体回退到"外壳直转旧实现"分支。
- **数据回退**：配置/任务文件原子写，写前备份（P0-9 已落地凭证备份范式），异常路径回滚原文件。

### 7.3 验收标准（硬性）
- 全量 `dotnet test BatchAgentRunner.slnx` **0 失败**（基线 345，随阶段递增）；
- `dotnet build --no-incremental` **0 警告 / 0 错误**（`TreatWarningsAsErrors`）；
- ArchUnitNET 分层断言全绿（Core 不越层、Desktop 不 new 具体类型、无 `Process` 进 Core、无 `INotifyPropertyChanged` 进 Domain）；
- 复杂度阈值达标：最大文件 ≤800 行、最大方法 ≤60 行、圈复杂度 ≤15、构造参数 ≤7；
- `catch (Exception)` 占比逐阶段下降；无空 `catch { }`；
- Desktop 测试 ≥40 项；高危模块零覆盖数 → 0；
- 对外契约（配置 schema / 任务文件格式 / CLI 参数 / 报告格式）字节级等价，用户操作流程不变。
